# Bottom line

**Start with PostgreSQL + pgvector, but not as a single global HNSW index over all 2,000 organizations.** The viable design is:

- `halfvec(1536)` for the indexed vector,
- tenant-aware physical partitioning with a per-partition HNSW index,
- row-level security for organization scoping plus an explicit document-ACL join,
- `pg_search` BM25 plus reciprocal-rank fusion for hybrid ranking.

A naive pgvector deployment—one 5M-row HNSW index, post-filtering on `tenant_id`, and Postgres full-text search alone—is the design I would rule out.

Keep **Qdrant as the pre-approved escape hatch**, not a parallel system from day one. Choose **OpenSearch** only if keyword search, analyzers, phrase/facet behavior, and a mature document-level security plugin are strategic differentiators and you are prepared to operate a search cluster.

The reason is not that 5M vectors is large. It is that a 2,000-tenant corpus makes the average tenant only **2,500 chunks, or 0.05% of the corpus**. pgvector’s own documentation gives the failure mode: at 10% selectivity with the default `hnsw.ef_search = 40`, only about 4 of 40 candidates match [82]. At 0.05%, a global HNSW index is the wrong shape. Partitioning turns the tenant filter into a local, much less selective problem.

# Why this workload is deceptive

| Dimension | Implication |
|---|---|
| 5M chunks × 1,536 dims | Roughly 31 GB of raw float32 vectors; not a “big data” vector problem [82] |
| 2,000 organizations | Average 2,500 chunks/org; tenant skew will matter more than corpus size |
| 50 searches/sec | About 5 concurrent requests at 100 ms each; raw ANN throughput is unlikely to be the binding constraint |
| p95 < 300 ms end-to-end | Must include query embedding, ACL resolution, hybrid retrieval, fusion, reranking, and network—not just vector search |
| Keyword + semantic + frequent updates | Requires two retrieval paths, fusion, and a write path that does not degrade search |
| Document permissions | The hardest requirement; a highly selective ACL filter can defeat ANN recall even inside a tenant |

Published single-node tests at 1M × 1,536 report 146–225 QPS at high recall with one thread [434][505]. At 5M, 50 QPS is plausible on modest hardware. The risks are **filtered recall, tail latency under updates, and permission correctness**, not raw QPS.

# Sizing: what 5M vectors actually costs

## Formulas

- pgvector `vector`: `4 × dimensions + 8` bytes per row; `halfvec`: `2 × dimensions + 8` [82].
- Qdrant HNSW graph: `base × m × 2 × 4 bytes × 1.2`, where `base = points × replication_factor` [173].
- OpenSearch 7-bit Lucene scalar quantization: `1.1 × (dimension + 8 × M)` bytes/vector [189]; the float32 equivalent uses `4 × dimension` in the same layout [519].

## Estimated footprint, one copy

| 5M × 1,536 | pgvector `vector` | pgvector `halfvec` | Qdrant float32 | OpenSearch float32 |
|---|---:|---:|---:|---:|
| Vector payload | 30.8 GB | 15.4 GB | 30.7 GB | included in native |
| ANN index / graph | ~38.7 GB | ~19.3 GB | ~0.8 GB | ~34.5 GB native |
| IDs / metadata | table overhead | table overhead | ~0.3 GB | text/doc values extra |
| **Total before text, ACLs, headroom** | **~69.5 GB** | **~34.7 GB** | **~31.8 GB** | **~34.5 GB + heap/text** |
| Quantized option | binary index ~2.4 GB + table 30.8 GB | — | binary ~2 GB RAM + full vectors on disk | 7-bit scalar ~9.2 GB |

The pgvector index figures are a linear extrapolation from a measured 1M × 1,536 index: 7,734 MB for full `vector`, 3,867 MB for `halfvec`, and 473 MB for binary quantization [505]. The Qdrant graph figure is the vendor formula [173]. The OpenSearch float32 figure is derived from the vendor’s HNSW layout formula [519]; its official 7-bit figure is about 9.2 GB per copy [189].

**What this means:**

- At 5M, **halfvec, Qdrant float32, and OpenSearch float32 are all roughly 32–35 GB per copy**. Memory is not the deciding factor.
- Full-precision pgvector is the outlier at ~70 GB because its HNSW index carries the vector plus graph links; measured index size is consistent with the 6.15 GB vector payload plus graph overhead [82][505].
- Add 20–30% for text, ACL tables, WAL, allocator overhead, and fragmentation. With HA, each replica/standby carries another full copy.
- For pgvector builds, `maintenance_work_mem` should hold the graph; a 5M halfvec graph is roughly 19 GB, so plan for 24–32 GB during index creation [82].
- For OpenSearch, the native-memory circuit breaker defaults to 50% of memory remaining after the JVM heap [181]. A 64 GB node with a 32 GB heap has only ~16 GB of native budget—not enough for a 34.5 GB float32 graph. You need larger nodes, more data nodes, or scalar quantization.

# Option assessment

## PostgreSQL + pgvector

### Hybrid ranking

pgvector does not provide BM25. Its documented hybrid approach is Postgres full-text search plus vector search, combined with RRF or a cross-encoder [82]. Postgres `ts_rank_cd` scores documents largely in isolation and lacks global inverse-document-frequency and BM25 term saturation [199]. For a B2B knowledge product where product codes, names, and exact phrases matter, that is a real relevance gap.

The fix is **ParadeDB `pg_search`**, which adds BM25 as a native Postgres index. It requires pgvector as a dependency, `shared_preload_libraries = 'pg_search'`, superuser access, and PostgreSQL 15+ for prebuilt binaries [207]. The hybrid query is one SQL statement with two CTEs—BM25 and vector—fused by RRF, typically with `k = 60` [199].

**Caveat:** many managed PostgreSQL services do not allow `shared_preload_libraries` or superuser extension installation. Confirm this before committing. If `pg_search` is unavailable, Postgres FTS + RRF is a weaker v1; Qdrant’s native BM25 + dense hybrid becomes more attractive.

### Filtered vector search

pgvector applies filters **after** the approximate index scan. The documentation’s example is explicit: a 10% filter with `ef_search = 40` yields about 4 matching rows [82]. Iterative index scans, added in 0.8.0, continue scanning until enough rows match or `hnsw.max_scan_tuples` (default 20,000) or a memory limit is reached [82].

The documentation also warns that sharing one approximate index across tenants means vectors from one tenant can affect recall and speed for another, and recommends list partitioning or separate tables for tenant isolation [82].

**Design implication:** do not use one 5M-row index. Use hash partitioning by `tenant_id` into roughly 64–256 partitions, with an HNSW index per partition. At 256 partitions, each holds about 19,500 chunks; a 2,500-chunk tenant is about 12.8% of its partition, close to the documented 10% case where iterative scanning works. PostgreSQL’s planner is documented to handle “up to a few hundred partitions fairly well,” with planning time and memory rising as partitions increase [708]. A 2,000-partition list is likely to hit planning overhead; promote only the largest tenants to dedicated partitions or tables.

Verify partition pruning with `EXPLAIN (ANALYZE)` under RLS. The query must include a direct `tenant_id = $1` predicate, not only a join condition.

### Permission enforcement

PostgreSQL RLS is the strongest centralized model of the three. It is default-deny once enabled, policies are evaluated before user-query predicates, and simple same-row policies are documented as the simplest and best-performing case [393]. Superusers, `BYPASSRLS` roles, and table owners normally bypass RLS; use a non-owner application role and `FORCE ROW LEVEL SECURITY` where appropriate [393]. Referential-integrity checks bypass RLS, so avoid exposing parent/child existence through constraint errors [393].

For document permissions, keep the RLS policy simple—organization scoping—and enforce document ACLs with an explicit join or a precomputed accessible-document set. Complex subqueries inside RLS policies can create race conditions and performance problems [393]. Test ACL revocation explicitly: in Postgres, a committed ACL change is visible to the next transaction, which is a major advantage over the alternatives.

### Updates and consistency

Postgres gives ACID transactions and WAL-backed durability [82]. Search sees committed changes immediately. The cost is HNSW maintenance: vacuuming HNSW indexes can be slow because it repairs graph connections; the documented workaround is `REINDEX INDEX CONCURRENTLY` followed by `VACUUM` [82]. Dead tuples and filtering can reduce HNSW results [82].

Use pgvector **0.8.7 (1 October 2026)**, the newest stable release in the changelog reviewed [98]. Releases 0.8.3 and 0.8.4 fixed HNSW vacuum corruption and “graph not repaired” errors, so older 0.8.x versions are a poor choice for an update-heavy workload [98]. Monitor dead tuples, index bloat, and vacuum lag per partition; schedule reindexes during low traffic.

### Backup and recovery

PostgreSQL’s WAL archiving plus base backups support point-in-time recovery to any time since the base backup, with documented caveats: whole-cluster restore only, a continuous WAL archive, and a working `restore_command` [414]. Synchronous replication guarantees no data loss on failover; asynchronous replication can lose recent transactions [636]. This is the strongest recovery story of the three.

### Operational burden

Lowest of the three for this team: one system, existing operational knowledge, one backup/HA model, one permission model. The added work is extension management, partition maintenance, HNSW vacuum/reindex, and `pg_search` installation. For six engineers, that is meaningfully less than operating a second distributed system.

## Qdrant

### Hybrid ranking

Qdrant has native hybrid retrieval. The Query API runs dense and sparse/BM25 prefetches and fuses them server-side with RRF or DBSF [223]. RRF’s default `k` is **2** in Qdrant, not the more common 60, and is configurable from 1.16 [223]. DBSF normalizes score distributions and can work better when raw scores are meaningful, but its normalization is based on the prefetch top-k and can be skewed by outliers [223].

Qdrant also supports BM25 full-text search on payload fields. A subtle multi-tenant issue: by default, BM25/IDF statistics are shard-wide, so one tenant’s documents affect another tenant’s ranking. Qdrant 1.19 adds an `idf` parameter to scope statistics to a tenant [24]. If you use BM25 hybrid, use 1.19+ and set it.

### Filtered vector search

This is Qdrant’s strongest area. It filters **during** the search: the planner either scores matching points directly when few match, or walks the HNSW graph while skipping non-matching points. Payload indexes supply cardinality estimates and extra “filterable HNSW” edges; ACORN handles multiple strict filters or graphs with many deleted points [26]. For a single indexed tenant field, the filterable-HNSW edges are designed for exactly this pattern, and ACORN is not needed [26].

Qdrant’s multitenancy guidance matches your shape: payload partitioning is recommended for “a large number of small, similarly-sized tenants,” with a keyword payload index on the tenant field and `is_tenant: true` to co-locate each tenant’s vectors [24]. For 2,000 tenants, do **not** create 2,000 collections; Qdrant’s guidance says collection-per-tenant does not scale past a few hundred and wastes resources [463]. If indexing speed becomes the bottleneck, set `m = 0` and `payload_m = 16` to build payload-aware links per tenant instead of a global graph [24].

### Permission enforcement

Qdrant’s RBAC is **collection-level**, not point-level: API keys and JWTs grant read/write or read-only access to whole collections [384]. There is no documented mechanism to restrict a tenant to only its own points within a shared collection. Tenant and document ACLs must be enforced by the application injecting payload filters.

That is a real security disadvantage versus RLS or DLS. Mitigate by never exposing Qdrant directly to clients, using a read-only collection-scoped key, centralizing query construction so every request injects the tenant/ACL filter, and adding integration tests that attempt cross-tenant queries. Keep permissions in Postgres as the system of record and pass a resolved filter to Qdrant; do not make Qdrant the ACL store.

### Updates and consistency

Qdrant defaults to availability and throughput, not strong consistency. Write ordering defaults to `weak`, reads default to consistency `1`, and a point may be visible on one replica but not another while updates propagate—“blinking” [276]. `write_consistency_factor` defaults to 1; setting it equal to the replication factor rejects unreplicated writes [276]. Strong write ordering serializes through a permanent leader but makes writes unavailable if the leader is down [276]. Point operations do not go through Raft, and Qdrant does not guarantee atomic distributed updates [619].

For frequent updates, unindexed segments are full-scanned until the optimizer indexes them, which can cause latency spikes. `indexed_only` skips unindexed segments but makes points blink; the experimental `prevent_unoptimized` withholds new points until their segment is optimized [535]. Monitor deferred points and optimizer queues. For ACL changes, use read consistency high enough for permission-sensitive queries, or resolve ACLs in Postgres before calling Qdrant.

### Backup and recovery

Qdrant snapshots are tar archives of a collection’s data and configuration on a specific node at a specific time; collection snapshots exclude aliases, and distributed collections require per-node snapshots [336]. No point-in-time recovery is documented. Qdrant’s production guidance recommends full backups for disaster recovery and snapshots primarily for moving data, and stresses testing restores [613]. Restoring a snapshot or migrating requires roughly twice the source disk and RAM on the target [173]. This is workable for a rebuildable vector index, but weaker than Postgres PITR.

### Operational burden

Medium-high. A production Qdrant deployment is at least **3 nodes with replication factor 2**, using Raft for cluster metadata, a load balancer, snapshots/backups, payload-index discipline, optimizer monitoring, and quantization tuning [619][613]. A single node is explicitly “not recommended for production” and “fragile” [619][613]. Running Qdrant alongside Postgres also means solving dual-write/CDC consistency: Postgres remains the source of truth, Qdrant must be idempotently updated, and the index must be rebuildable. That is a meaningful addition for six engineers.

## OpenSearch

### Hybrid ranking

OpenSearch has the richest keyword stack: analyzers, stemming, synonyms, phrase queries, highlighting, facets, and aggregations. Hybrid search combines lexical and k-NN clauses through a search pipeline. The normalization processor (2.10+) normalizes scores and combines them with arithmetic/geometric/harmonic means; the score-ranker processor (2.19+) implements RRF with a default `rank_constant` of 60 [135][590]. RRF is robust to incomparable score scales, but on six BEIR datasets it averaged **3.86% lower NDCG@10** than the score-based pipeline [590]. Pre-filtering with a top-level `filter` in the hybrid query, applied to both lexical and k-NN subqueries, was introduced in 3.0 [121].

For a B2B knowledge product, this is the best out-of-the-box keyword relevance. The question is whether you need that richness enough to pay the operational cost.

### Filtered vector search

OpenSearch’s “efficient k-NN filtering” applies filtering during the vector search and guarantees k results if at least k matches exist. It is supported for Lucene HNSW from 2.4, Faiss HNSW from 2.9, and Faiss IVF from 2.10 [128]. ACORN filtering, which explores neighbors-of-neighbors when filters make the graph sparse, is applied in 3.1+ when memory-optimized search is enabled [785].

The alternative is a scoring-script/pre-filter exact search, which can have high latency and does not scale when the filtered subset is large [128]. For a 2,500-chunk tenant, exact search is cheap. For a 500K-chunk tenant with a 0.1% ACL filter, it is not. OpenSearch can handle both paths, but you must test which path the planner chooses and what recall it delivers.

Current OpenSearch documentation lists a maximum of 16,000 dimensions for Lucene, Faiss, and JVector [784]; older Lucene documentation capped it at 1,024 [603]. Confirm your deployed version supports 1,536 with the engine you choose.

### Permission enforcement

OpenSearch’s Security plugin provides document-level security (DLS): a role can include a query DSL fragment that restricts which documents are retrievable [295]. DLS applies to search and get, but **not** to writes; a user with write permission can modify documents they cannot read [295]. The DLS configuration has a 1,024 KB limit, and the documentation recommends keeping DLS queries simple to minimize cluster performance impact [295].

For 2,000 organizations, you would need dynamic DLS—terms lookup or attribute-based security using `${user.roles}` or `${attr...}`—rather than 2,000 static roles [295]. Test this carefully. There was a real bug where hybrid search failed for users with DLS enabled, throwing a `ConstantScoreQuery cannot be cast to HybridQuery` error; it was fixed in neural-search **3.2.0.0**, compatible with OpenSearch 3.2.0 [751][764]. If you choose OpenSearch, require that version or later and run a DLS+hybrid acceptance test.

### Updates and consistency

OpenSearch is near-real-time: it refreshes each index every second by default, so a document becomes searchable about a second after indexing [354]. Durability comes from the translog and flush, not refresh [354]. Updates rewrite documents and create new segments; segment merges rebuild vector structures, and force merge is used to consolidate segments but is not routine on actively written indices [588][576]. For frequent updates, expect merge pressure and occasional latency spikes; monitor segment count and merge activity.

### Backup and recovery

Snapshots capture indexes and cluster state, including cluster settings, node information, index metadata, and shard allocation [368]. Restore is through the snapshot API; existing open indexes with the same name must be closed, deleted, or renamed [358]. No point-in-time recovery is documented. Export security roles/DLS configuration separately and test restore, because the snapshot documentation does not list security configuration among the captured state [368].

### Operational burden

Highest of the three. You are operating a JVM cluster with heap sizing, native-memory circuit breakers, shard planning, segment merges, snapshots, index templates/ISM, security plugin roles/DLS, and version upgrades. The k-NN circuit breaker alone requires careful capacity planning: native vector memory is capped at 50% of memory remaining after the JVM heap, and exceeding it evicts least-recently-used indexes [181]. For six engineers, this is justified only if keyword search and security features are core to the product.

# Which public benchmarks matter—and which do not

No public benchmark I reviewed matches **5M × 1,536 with tenant and document-ACL filters at 50 QPS and p95 latency**. That is the central finding. The benchmarks disagree partly because they measure different things.

| Benchmark | What it measures | Relevance to you | Why it is not decisive |
|---|---|---|---|
| **ANN-Benchmarks** | Single-thread, in-memory recall–QPS curves | Algorithm-level sanity check | No concurrency, filters, updates, or ACLs [685] |
| **Big-ANN NeurIPS’23 filtered track** | 10M × 192-dim uint8 CLIP, 1–2 tag filters, batch QPS at ≥90% recall@10 | Filtered ANN at scale | Wrong dimensions/type, no tenant/ACL filters, no p95, no updates [154] |
| **HSEB** | MS MARCO 384-dim, 10%/90%/100% filter selectivity, Pareto-tuned per engine | Filter-selectivity methodology | No published results in the README, no lexical hybrid despite the name, 384 dims [65] |
| **Tigerdata/Timescale 50M × 768** | pgvector + pgvectorscale StreamingDiskANN vs Qdrant, no filters | Throughput vs tail-latency trade-off | Vendor-run, 768 dims, no filters, pgvector alone not tested, Qdrant tuning caveats [243] |
| **Jonathan Katz 1M × 1536** | pgvector full vs halfvec vs binary, single-thread | Directly useful for pgvector sizing and quantization | No filters, no concurrency [505] |
| **Tencent Cloud 1M × 1536** | pgvector HNSW, single-thread, Recall@100 | Raw 1536-dim ANN sanity check | No filters, no concurrency, only two configurations [434] |
| **VectorDBBench** | 5M × 1536 search, filtered label cases, concurrency sweeps, insertion-under-load | Closest harness to reuse | Filtered cases are label/int filters, not tenant/ACL; no ACL benchmark; QPS is highest observed, not a p95 SLO [687] |
| **Qdrant quantization benchmarks** | Binary/TurboQuant recall at 100K × 1536 | Quantization recall sanity check | Small scale, vendor-run [830][836] |

Two concrete examples of why the numbers disagree:

- One 2026 comparison found Qdrant had the **slowest search but fastest index build**, while other comparisons rank Qdrant as the lowest-latency engine [876][863]. Different datasets, index configurations, and tuning produce different winners.
- Tigerdata’s 50M benchmark reports Qdrant with lower p95 latency but far lower throughput than Postgres + pgvectorscale at 99% recall [243]. That is a throughput-versus-tail-latency trade-off, not a universal ranking—and it did not test filters.

A 2026 VLDB paper makes the methodological point directly: filtered ANN performance is highly sensitive to how attributes, filters, and queries are constructed; even with the same vectors and index, different label-synthesis policies can change the ranking of methods [139]. Its full PDF was unavailable in this review, so treat that as a research finding rather than a verified production benchmark.

**The relevant conclusion:** use public benchmarks to choose candidate configurations and to sanity-check orders of magnitude, not to select the engine. The only benchmark that answers your question is the one you run on your corpus, your tenant distribution, your ACL distribution, and your query mix.

# What you must measure yourselves

## Test corpus

Build a representative 5M-chunk corpus, or a stratified sample large enough to preserve tail behavior:

- **Tenant skew:** not 2,500 chunks each. Use a Zipf-like distribution—for example, top 1% of tenants own 30–40% of chunks, median tenant 1,000–2,500, largest tenant 100K–500K.
- **ACL selectivity:** bucket document permissions at 100%, 10%, 1%, and 0.1% of a tenant’s documents. The 0.1% bucket is where ANN recall often collapses.
- **Query mix:** 40% keyword-heavy, 40% semantic, 20% mixed; include product codes, exact phrases, and natural-language questions.
- **Ground truth:** compute exact top-k per tenant and per ACL bucket with brute force. Do not use global ground truth; it hides tenant-level failures.
- **Updates:** replay a realistic change rate—new documents, re-embedded chunks, ACL changes, deletions. Test at 5%, 20%, and 50% of the corpus per day if those are plausible.

## Measurements

| Dimension | What to record | Suggested pass criterion |
|---|---|---|
| **End-to-end latency** | p50/p95/p99 for the full request, plus per-stage: auth/ACL, embedding, retrieval, fusion, rerank, network | p95 ≤ 300 ms at 50 QPS; p99 ≤ 500 ms; 100 QPS for 10 min without >20% degradation |
| **Filtered recall** | Recall@10 and Recall@50 vs exact, per tenant-size bucket and ACL-selectivity bucket | ≥ 0.90 in every bucket, especially p95 tenant and 0.1% ACL |
| **Result completeness** | Empty-result rate and “fewer than k” rate | ≤ 1% empty; no systematic short results |
| **Relevance** | nDCG@10 on labeled queries: keyword-only, semantic-only, hybrid | Hybrid beats both single retrievers; pre-register the target |
| **Update behavior** | Time-to-searchable for new docs and ACL changes; p95 during sustained updates; vacuum/optimizer backlog | New docs and ACL revocations visible ≤ 5 s p95; p95 stays ≤ 300 ms under 2× expected update rate |
| **Memory/disk** | RSS, cache hit rate, index size, build time, WAL/segment growth | Index fits in RAM or has acceptable disk latency; 30% headroom |
| **Failure/recovery** | Node kill, failover, snapshot restore, PITR replay | RTO/RPO meet business requirements; restore tested, not just configured |
| **Cost** | Infrastructure per month plus engineering hours per month | Within budget; ops toil sustainable for six engineers |

## Test each engine at its best configuration

Do not compare defaults. For pgvector, tune `m`, `ef_construction`, `ef_search`, `iterative_scan`, `max_scan_tuples`, partition count, and `work_mem`. For Qdrant, tune `m`, `payload_m`, `hnsw_ef`, payload indexes, quantization, and `is_tenant`. For OpenSearch, tune engine (Lucene vs Faiss), `m`, `ef_construction`, `ef_search`, shard count, quantization, and ACORN. Use the same hardware class, client, query embeddings, and k.

# Exit criteria: when to move away

## Move from pgvector to Qdrant if

- **Filtered recall fails:** Recall@10 falls below your target (for example, < 0.90) in the p95 tenant-size or 0.1% ACL bucket after tuning partitions, `ef_search`, and iterative scans.
- **Empty/short results persist:** More than ~1–2% of queries return no results or fewer than k in a tenant/ACL slice.
- **Tail latency fails:** p95 > 300 ms at 50 QPS, or p99 > 500 ms, while CPU is below ~60% and the index is cached—meaning the problem is algorithmic, not capacity.
- **Update churn breaks search:** HNSW vacuum/reindex causes recurring p95 breaches, index bloat exceeds ~2×, or reindexing cannot finish inside your maintenance window.
- **Large-tenant skew dominates:** A small number of tenants have hundreds of thousands of chunks and their ACL filters cannot be served with acceptable recall despite dedicated partitions.
- **Operational toil exceeds capacity:** More than ~20% of engineering time goes to search infrastructure for two consecutive months.

## Move from pgvector to OpenSearch if

- Keyword relevance is the main gap: analyzers, synonyms, phrase matching, faceting, or highlighting cannot be matched with `pg_search` + RRF.
- You need a search platform for other product surfaces, not just vector retrieval.
- DLS is a better fit for your security model than RLS + SQL ACL joins—and you have validated DLS+hybrid on OpenSearch 3.2+ (neural-search 3.2.0.0) [764].

## Move away from Qdrant if

- Cross-tenant filter enforcement proves error-prone, or ACL propagation lag violates revocation requirements.
- Replica inconsistency (“blinking”) affects permission-sensitive results despite read-consistency tuning [276].
- Snapshot restore or version upgrades fail in practice; no PITR is a business blocker [336].
- Operating a 3-node cluster plus dual-write synchronization consumes more capacity than the team has.

## Scale trigger

Re-evaluate the architecture at **>20M chunks** or **>150–200 QPS sustained**. At 5M and 50 QPS, scale is not the reason to move; filtered recall, permissions, and update behavior are.

# Recommended plan

## Phase 0: two-week proof (before committing)

1. Build the 5M stratified corpus with tenant skew and ACL buckets.
2. Load into pgvector `halfvec(1536)`, hash-partitioned into 64–256 partitions, with per-partition HNSW.
3. Implement hybrid retrieval with `pg_search` BM25 + RRF; if `pg_search` is unavailable, test Postgres FTS + RRF and record the relevance gap.
4. Measure end-to-end p95 at 50 QPS, filtered recall per bucket, update churn, and vacuum behavior.
5. In parallel, run the same corpus through a Qdrant single-collection `is_tenant` configuration and an OpenSearch configuration. This is a **bake-off**, not a production commitment.

**Go/no-go:** If pgvector meets the latency and recall thresholds, proceed. If not, the failure mode tells you which escape hatch to choose: recall/filtering → Qdrant; keyword relevance → OpenSearch; operational simplicity → revisit pgvector partitioning.

## Phase 1: productionize PostgreSQL (4–6 weeks)

- Schema: `chunks` partitioned by `HASH(tenant_id)`; columns for `tenant_id`, `document_id`, `chunk_text`, `embedding halfvec(1536)`, ACL fields, `updated_at`, embedding version.
- HNSW per partition with `m = 16`, `ef_construction = 64–128`; query with `hnsw.ef_search` tuned, `hnsw.iterative_scan = relaxed_order`, `hnsw.max_scan_tuples` tuned.
- RLS on `tenant_id`; non-owner application role; `FORCE ROW LEVEL SECURITY`; `SET LOCAL app.tenant_id` per transaction.
- Document ACL: `document_acl` table or `allowed_group_ids` array with GIN; explicit join; test revocation.
- BM25: `pg_search` index on chunk text; hybrid SQL with RRF; tune weights on a train/validation split.
- Updates: idempotent upserts, embedding-version backfill, batch writes, autovacuum tuning, per-partition `REINDEX CONCURRENTLY` runbook.
- HA/backup: synchronous standby or managed HA; WAL archiving to object storage; monthly restore drill.
- Observability: `pg_stat_statements`, `auto_explain`, `pg_buffercache`, per-tenant p95, vacuum lag, index bloat.

## Phase 2: conditional Qdrant pilot

Trigger only if the exit criteria fire. Keep Postgres as the source of truth:

- Outbox/CDC from Postgres to Qdrant; idempotent upserts keyed by chunk ID.
- One Qdrant collection, `tenant_id` keyword index with `is_tenant: true`, ACL fields indexed.
- `m = 0`, `payload_m = 16` if indexing is the bottleneck; otherwise default `m = 16`.
- Quantization (scalar int8 or binary + rescore) only after recall testing; binary at 1,536 dims can reach ~0.985 recall with 3× oversampling in Qdrant’s 100K benchmark, but validate on your data [830].
- 3 nodes, replication factor 2, read consistency appropriate for ACL-sensitive queries, snapshots plus full backups.
- Rebuildable index: if Qdrant is lost, rebuild from Postgres; never make it the only copy.

# Assumptions and evidence gaps

These are material and should be resolved before the final decision:

- **Update rate:** “Frequent” is undefined. The design changes materially if 50% of the corpus is re-embedded daily versus 2%.
- **ACL complexity:** Organization-only is easy; group/user/document-inherited ACLs with instant revocation are much harder. The 0.1% ACL bucket is the key stress case.
- **Deployment model:** Self-managed versus managed PostgreSQL determines whether `pg_search` is available. It requires `shared_preload_libraries` and superuser [207].
- **Embedding and reranking latency:** The 300 ms budget is end-to-end. If query embedding takes 80 ms and reranking takes 100 ms, retrieval must fit in ~100 ms. Measure the full path, not just the database.
- **Tenant size distribution:** The 2,500 average hides the largest tenants. A 500K-chunk tenant with a selective ACL is a different problem from a 2,500-chunk tenant.
- **Recall and relevance targets:** “Good search” is not a number. Pre-register Recall@10 and nDCG@10 targets per bucket.
- **Growth:** 5M/2,000/50 QPS is the stated scope; if 20M/10,000/200 QPS is plausible within two years, plan the partitioning and escape hatch now.

Evidence limitations:

- No public benchmark reviewed matches 5M × 1,536 with tenant and document-ACL filters at 50 QPS and p95. The closest harness is VectorDBBench, but its filtered cases are label/int filters, not ACLs [687].
- The 2026 filtered-ANN paper was available only as a search-content extract, not a verified full PDF [139].
- OpenSearch’s official DLS page does not explicitly document k-NN/hybrid behavior; the hybrid+DLS bug and its fix are documented in the neural-search issue and release notes [751][764]. Test the exact deployed version.
- `pg_search` support for partitioned tables and your PostgreSQL version was not verified; confirm before committing to the partition layout.
- Qdrant snapshot format compatibility across versions was not stated in the snapshot documentation [336]; test restore on the versions you will run.
- The pgvector 5M index sizes are linear extrapolations from 1M measurements [505], and the OpenSearch float32 figure is derived from the vendor’s HNSW layout formula [519]. Treat them as planning estimates and measure your own build.
