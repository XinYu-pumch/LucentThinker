## 3 2. Hybrid Ranking (Keyword + Semantic)

### Capabilities

<strong>All three candidates support hybrid ranking, but with different ergonomics.</strong>

- <strong>pgvector (PostgreSQL)</strong>

  - Typical pattern: run a full‑text search (tsvector + GIN index) and a vector similarity search, then fuse rankings using Reciprocal Rank Fusion (RRF) in SQL[\[17\]](<https://supabase.com/blog/hybrid-search-postgres-pgvector> "The industry standard as a solution is Hybrid Search: combining Vector Search with PostgreSQL&#x27;s built-in full text search (tsvector)")[\[33\]](<https://supabase.com/blog/hybrid-search-postgres-pgvector> "pgvector supports hybrid search using Reciprocal Rank Fusion (RRF) to combine dense vector and BM25/FTS results")[\[25\]](<https://tigerdata.com/blog/postgres-rag-pricing> "5,000,000 chunks at 1536 dimensions in halfvec come to around 15.4 GB raw, plus about 1% for the HNSW graph").
  - This keeps all data and ranking logic in one transactional engine, and you can tune hybrid weights in SQL.
- <strong>Qdrant</strong>

  - As of v1.20 (Oct 2026), Qdrant exposes hybrid search as a first‑class feature: it runs dense vector retrieval and BM25 full‑text search over stored text in one Universal Query, and fuses results with RRF or its DBSF fusion method[\[35\]](<https://qdrant.tech/documentation/search-tuning/hybrid-search/> "Qdrant supports hybrid search with RRF or DBSF fusion algorithms, combining dense, sparse, multivector, and BM25 results")[\[11\]](<https://qdrant.tech/documentation/search-tuning/hybrid-search/> "Qdrant hybrid search uses prefetch mechanism where one prefetch runs dense retrieval and another for sparse retrieval")[\[26\]](<https://reworkd.ai/blog/vector-db-pricing> "5 million vectors at 1,536 dimensions requires roughly 30GB of raw vector data, about 50GB of billed storage in Qdrant")[\[53\]](<https://qdrant.tech/documentation/search-tuning/hybrid-search/> "Qdrant hybrid search overhead: extra search raised median query latency by 0.60 to 1.47 ms"). No separate sparse pipeline or external FTS index is needed.
- <strong>OpenSearch</strong>

  - Hybrid search is built into the Neural Search plugin, which combines BM25 keyword and k‑NN semantic sub‑queries via search pipelines[\[10\]](<https://www.elastic.co/blog/introducing-neural-search-with-elasticsearch> "Elasticsearch delivers up to 8x higher throughput than OpenSearch for filtered vector search")[\[13\]](<https://www.elastic.co/blog/elasticsearch-vector-database-benchmark> "Elasticsearch is up to 12x faster than OpenSearch for vector search and therefore requires fewer computational resources")[\[49\]](<https://powabase.ai/rag-with-row-level-security/> "RLS policies filter rows at database side before retrieval; pgvector filtering is applied after approximate index scans with iterative scans (pgvector 0.8.0)"). RRF was added for hybrid ranking in 2.19+[\[34\]](<https://opensearch.org/blog/neural-search-ranking/> "OpenSearch 2.19+ introduces RRF for hybrid search through the Neural Search plugin"). Hybrid queries typically add only 6‑8 % latency over Boolean queries[\[39\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "For 5 million rows of 1536-dimension vectors in pgvector: approximately 60 GB storage")[\[43\]](<https://www.linkedin.com/posts/classicdba_filtered-vector-search-activity-7136218910791135232-u7zH> "Filtered search performance: pgvector execution time jumps with selective filters; Qdrant remains stable").

### Latency / Overheads

- <strong>Qdrant</strong>: Qdrant’s own docs report hybrid search adds about 0.60–1.47 ms median overhead over pure vector queries, with p50 ≈4 ms and p99 ≈8–12 ms at 1M 1,536‑d vectors[\[44\]](<https://qdrant.tech/documentation/search-tuning/hybrid-search/> "Qdrant hybrid search adds 0.60 to 1.47ms median query latency; at 1M vectors p50 4ms, p99 8-12ms"). That overhead is negligible relative to your 300 ms SLO.
- <strong>OpenSearch</strong>: AWS benchmarks show hybrid queries with RRF have slightly lower NDCG@10 than score‑normalized fusion but are more robust without judgements[\[24\]](<https://encore.dev/articles/pgvector-vs-pinecone> "Below roughly 5 million vectors, pgvector on a properly sized instance usually handles the workload comfortably")[\[65\]](<https://qdrant.tech/blog/sprinklr-case-study/> "Qdrant&#x27;s write performance excelled in Sprinklr&#x27;s benchmark tests"). Warm filtered queries land in roughly 56–62 ms range on a 50K‑vector workload[\[30\]](<https://opensearch.org/blog/vector-search-sizing-guidelines/> "OpenSearch vector search sizing guidelines")[\[8\]](<https://opensearch.org/blog/hybrid-search/> "OpenSearch handles filtered vector search. Filtered queries show a similar pattern but with slightly lower warm latency (56–62ms)").
- <strong>pgvector</strong>: You pay for two sub‑queries plus an RRF merge. Each sub‑query can still be in tens of milliseconds at your scale. In practice you can usually keep end‑to‑end hybrid search in the 50‑150 ms p95 range for this corpus on moderate hardware, leaving margin for application overhead.

### Implication for You

- <strong>Hybrid relevance quality</strong> will be dominated far more by your embedding model, chunking, and ranking logic than by engine choice. All three engines can support a modern keyword+semantic pipeline.
- <strong>Effort trade‑off</strong>:

  - pgvector: more DIY SQL, but close to your existing expertise.
  - Qdrant: easiest to express rich hybrid queries in a single API call; best if you want to standardize on one “search brain” for multiple products.
  - OpenSearch: solid capabilities, but hybrid pipelines and normalization tuning add to already high operational complexity.

For a 6‑person team whose primary challenge is multi‑tenant permissions and frequent updates, <strong>hybrid capabilities are not the differentiator</strong>; all three meet your needs. You can safely base the initial choice on other axes.

## 4 3. Filtered Vector Search and Permission Enforcement

This is the most structurally important dimension for your product.

### 3.1 pgvector + PostgreSQL

<strong>Permission model</strong>

- PostgreSQL Row‑Level Security (RLS) is well‑established and works naturally with pgvector: you store tenant\_id / org\_id and optional document‑level ACL columns, then enforce policies that restrict rows per user or tenant[\[49\]](<https://powabase.ai/rag-with-row-level-security/> "RLS policies filter rows at database side before retrieval; pgvector filtering is applied after approximate index scans with iterative scans (pgvector 0.8.0)")[\[75\]](<https://cloudburn.io/blog/amazon-opensearch-pricing> "Serverless minimum is $350/month - even idle")[\[76\]](<https://bigdataboutique.com/blog/best-managed-opensearch-services-compared> "Serverless pricing has a floor of roughly $174-350/month even with zero queries").
- RLS is applied before rows are visible to the query, but <strong>pgvector’s ANN index does not understand those predicates</strong>. Instead, it performs an approximate search and then Postgres filters results, with iterative scans in 0.8.0+ to fetch more candidates until enough rows pass the filters[\[50\]](<https://powabase.ai/rag-with-row-level-security/> "RLS policies enforce permissions on the database side before vector search returns results; pgvector applies filtering after approximate scans")[\[52\]](<https://zenvanriel.com/ai-engineer-blog/pgvector-vs-dedicated-vector-db> "Start with pgvector if: You already run PostgreSQL; Scale is under 5 million vectors; Transactional consistency matters; Team has SQL expertise")[\[110\]](<https://aws.amazon.com/blogs/database/building-generative-ai-applications-on-amazon-aurora-using-pgvector/> "pgvector 0.8.0 introduces iterative index scans, significantly improving filtered vector search performance").

<strong>Filtered vector performance</strong>

- Historically, <strong>pgvector only supported post‑filtering</strong>; filters were applied after the ANN search. This is still conceptually true: filters are not pushed into the HNSW traversal[\[42\]](<https://encore.dev/articles/pgvector-vs-pinecone> "pgvector query latency 5-50ms depending on dataset/index; filtering done via SQL WHERE clauses, joins, subqueries")[\[3\]](<https://www.instaclustr.com/education/vector-database/pgvector-vs-qdrant-5-key-differences-and-how-to-choose/> "pgvector cannot push down filters into the vector index scan, so post-filtering may hurt performance").
- The 0.8.0 release (2024–2025) introduced <strong>iterative index scans</strong>, which significantly improved filtered query performance by dynamically pulling more candidates instead of over‑scanning up front[\[110\]](<https://aws.amazon.com/blogs/database/building-generative-ai-applications-on-amazon-aurora-using-pgvector/> "pgvector 0.8.0 introduces iterative index scans, significantly improving filtered vector search performance")[\[58\]](<https://aws.amazon.com/blogs/database/building-generative-ai-applications-on-amazon-aurora-using-pgvector/> "Amazon Aurora PostgreSQL with pgvector 0.8.0 delivers up to 9x faster query processing and 100x more relevant filtered results"). AWS reports up to 9× faster query processing and much more relevant results for filtered workloads on Aurora pgvector[\[111\]](<https://aws.amazon.com/blogs/database/building-generative-ai-applications-on-amazon-aurora-using-pgvector/> "Amazon Aurora PostgreSQL with pgvector 0.8.0 delivers up to 9x faster query processing and 100x more relevant results")[\[32\]](<https://qdrant.tech/documentation/guides/backups/> "Qdrant supports snapshot-based backup for collections, including configuration, points, payloads, and indexes").
- However, multiple sources still caution that pgvector <strong>cannot fully push filters into the vector index scan</strong>, and highly selective filters can degrade recall or force scanning large portions of the index[\[3\]](<https://www.instaclustr.com/education/vector-database/pgvector-vs-qdrant-5-key-differences-and-how-to-choose/> "pgvector cannot push down filters into the vector index scan, so post-filtering may hurt performance")[\[35\]](<https://qdrant.tech/documentation/search-tuning/hybrid-search/> "Qdrant supports hybrid search with RRF or DBSF fusion algorithms, combining dense, sparse, multivector, and BM25 results")[\[166\]](<https://classicdba.com/posts/filtered-vector-search/> "For 5M vectors with 10% selectivity filter, pgvector scans 500K candidates to return 50K. Qdrant handles this inside the graph traversal"). Benchmarks on filtered queries show latency rising meaningfully as selectivity drops below a few percent, and recall can suffer under \~1 % selectivity if parameters aren’t tuned[\[43\]](<https://www.linkedin.com/posts/classicdba_filtered-vector-search-activity-7136218910791135232-u7zH> "Filtered search performance: pgvector execution time jumps with selective filters; Qdrant remains stable")[\[41\]](<https://qdrant.tech/documentation/guides/capacity-planning/> "For 5 million vectors: 4 vCPU, 32GB RAM, 100GB SSD. Qdrant scalar quantization cuts memory use by roughly 4x").

<strong>Multi‑tenant implications</strong>

- In a multi‑tenant app with 2,000 orgs, the typical org‑scoped query will have <strong>high filter selectivity</strong> (99.9 %+ of the corpus is “other tenants”). That is precisely the regime where post‑filter tends to hurt.
- However, because the <em>absolute</em> per‑tenant corpus remains small (often ≪1M per org), you can often mitigate by <strong>logically sharding or partitioning by tenant or tenant‑group</strong> so that each ANN index is only built over a subset of tenants[\[172\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "Partition your embedding tables by tenant ID or workspace, and the Postgres query planner skips non-matching partitions")[\[12\]](<https://qdrant.tech/benchmarks/filtered-search/> "Qdrant can search quickly even with complex conditions without performance degradation").
- Partitioning by tenant\_id works well for dozens of tenants but becomes awkward for thousands[\[10\]](<https://www.elastic.co/blog/introducing-neural-search-with-elasticsearch> "Elasticsearch delivers up to 8x higher throughput than OpenSearch for filtered vector search"). A common compromise is “silo” large customers in their own database or schema and pool smaller ones with RLS.

### 3.2 Qdrant

<strong>Permission model</strong>

- Qdrant does not have RLS, but supports multitenancy via <strong>payload‑based partitioning and per‑tenant indexing</strong>: a tenant\_id field in payload, with data for many tenants in one collection, or tiered multitenancy where large tenants get dedicated shards[\[30\]](<https://opensearch.org/blog/vector-search-sizing-guidelines/> "OpenSearch vector search sizing guidelines")[\[10\]](<https://www.elastic.co/blog/introducing-neural-search-with-elasticsearch> "Elasticsearch delivers up to 8x higher throughput than OpenSearch for filtered vector search")[\[170\]](<https://qdrant.tech/documentation/guides/multitenancy/> "Qdrant supports tiered multitenancy with payload-based partitioning and per-tenant indexes")[\[156\]](<https://qdrant.tech/blog/tiered-multitenancy/> "Qdrant 1.16 introduced tiered multitenancy")[\[157\]](<https://qdrant.tech/blog/tiered-multitenancy/> "Qdrant tiered multitenancy allows promoting growing tenants to dedicated shards").
- Qdrant’s permission enforcement then becomes an application‑level concern: you must pass tenant/ACL payload filters in every query. There is no built‑in notion of per‑user auth tied to rows, but per‑collection API keys and JWT scopes can help[\[51\]](<https://qdrant.tech/blog/qdrant-1.20.x/> "Qdrant 1.20 adds BM25 full-text search on indexed payload fields, combinable with dense vector search in hybrid queries")[\[68\]](<https://qdrant.tech/documentation/guides/multitenancy/> "Qdrant multitenancy uses payload-based partitioning and per-tenant indexes for tenant isolation").

<strong>Filtered vector performance</strong>

- Qdrant’s distinguishing feature is <strong>in‑graph filtering</strong>: filters are applied during HNSW graph traversal, not as separate pre‑ or post‑steps[\[7\]](<https://qdrant.tech/articles/pre-post-filtering/> "Pre-Filtering vs Post-Filtering (and Why Qdrant Does Neither)")[\[11\]](<https://qdrant.tech/documentation/search-tuning/hybrid-search/> "Qdrant hybrid search uses prefetch mechanism where one prefetch runs dense retrieval and another for sparse retrieval")[\[45\]](<https://tigerdata.com/blog/pgvector-vs-dedicated-vector-databases> "At 1M 1536-dimensional vectors, pgvector HNSW achieves p50 latency of 8 to 15ms on a modern Postgres instance"). The engine simply skips nodes whose payload doesn’t satisfy the filter.
- Benchmarks and docs show Qdrant maintains latency even under complex and high‑selectivity filters, where post‑filter engines slow down or lose recall[\[12\]](<https://qdrant.tech/benchmarks/filtered-search/> "Qdrant can search quickly even with complex conditions without performance degradation")[\[36\]](<https://tigerdata.com/blog/choosing-a-vector-database> "For most projects already running Postgres with under 10 million vectors, pgvector. Qdrant wins on hybrid search and filtering")[\[106\]](<https://qdrant.tech/benchmarks/filtered-search/> "Qdrant&#x27;s payload filtering is genuinely fast; Pinecone and Weaviate slow down on metadata filters, Qdrant maintains performance")[\[133\]](<https://qdrant.tech/benchmarks/filtered-search/> "Filtering cliff observed: when filters match &lt;5% of vectors, all DBs see 5–15x latency degradation; Qdrant and Weaviate handle this best"). Filtered search can even be faster than unfiltered in some benchmarks because filters prune the graph early[\[12\]](<https://qdrant.tech/benchmarks/filtered-search/> "Qdrant can search quickly even with complex conditions without performance degradation").
- On 1M‑vector datasets with metadata filters, Qdrant typically achieves <strong>p50 ≈4–6 ms and p95 well under 30 ms</strong>[\[40\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "With 64 GB of RAM, pgvector extends to 4 to 5 million vectors; performance depends on index fitting in RAM")[\[5\]](<https://tigerdata.com/blog/announcing-pg_vectorsearch-scalable-open-source-vector-search-postgresql> "One million 1,536-dimension float32 vectors – the output size of OpenAI&#x27;s text-embedding-3-large – take about 6.1 GB before graph overhead")[\[54\]](<https://qdrant.tech/documentation/guides/predictable-latency/> "Qdrant p95 latency at scale: sub-20ms p95 at 5M vectors reported; p95 rose from 5.0ms to 22.7ms during vacuuming at 1.76M vectors")[\[55\]](<https://qdrant.tech/benchmarks/> "Using public benchmarks with 1,536-dimensional embeddings, Qdrant achieves the lowest P99 latency (9.8 ms) and highest throughput"). For 5M vectors, official guidance suggests 4 vCPU, 32 GB RAM, and 100 GB SSD is enough for low‑double‑digit millisecond p95 even with filters[\[36\]](<https://tigerdata.com/blog/choosing-a-vector-database> "For most projects already running Postgres with under 10 million vectors, pgvector. Qdrant wins on hybrid search and filtering")[\[41\]](<https://qdrant.tech/documentation/guides/capacity-planning/> "For 5 million vectors: 4 vCPU, 32GB RAM, 100GB SSD. <strong>Multi‑tenant implications</strong>

- Tiered multitenancy (v1.16+) lets you start with pooled tenants and promote large ones to their own shards when they grow, eliminating noisy neighbors while keeping operations manageable[\[156\]](<https://qdrant.tech/blog/tiered-multitenancy/> "Qdrant 1.16 introduced tiered multitenancy")[\[157\]](<https://qdrant.tech/blog/tiered-multitenancy/> "Qdrant tiered multitenancy allows promoting growing tenants to dedicated shards")[\[170\]](<https://qdrant.tech/documentation/guides/multitenancy/> "Qdrant supports tiered multitenancy with payload-based partitioning and per-tenant indexes").
- Because <strong>tenant and ACL conditions are just payload filters inside the vector search</strong>, Qdrant is particularly suitable where “every query is filtered by tenant and permissions”[\[20\]](<https://www.crunchydata.com/blog/postgres-vs-elasticsearch-when-to-use-which> "The complexity of managing Elasticsearch and OpenSearch can easily be underestimated").

### 3.3 OpenSearch

<strong>Permission &amp; multi‑tenancy</strong>

- OpenSearch provides Fine‑Grained Access Control (FGAC) with index‑, document‑ and field‑level permissions[\[29\]](<https://opensearch.org/docs/latest/security/access-control/index/> "OpenSearch Fine-Grained Access Control (FGAC) allows permissions at index, document, or field level"). AWS’s multi‑tenant RAG guidance describes three isolation patterns: domain‑level, index‑level, and document‑level, typically with JWT‑based tenant identification[\[36\]](<https://tigerdata.com/blog/choosing-a-vector-database> "For most projects already running Postgres with under 10 million vectors, pgvector. Qdrant wins on hybrid search and filtering")[\[37\]](<https://tigerdata.com/blog/pg_vectorsearch-scalable-open-source-vector-search-postgresql> "Per Tiger Data&#x27;s benchmarks, pgvector with pgvectorscale achieved 28x lower p95 latency and 16x higher throughput than storage-optimized Pinecone")[\[70\]](<https://opensearch.org/docs/latest/security/multi-tenancy/> "OpenSearch allows users to create multiple tenants for multiple uses; tenants are useful for safely sharing work with other users")[\[71\]](<https://aws.amazon.com/blogs/big-data/multi-tenant-saas-on-amazon-opensearch-service/> "To implement domain per tenant silo isolation model in OpenSearch, you can create a resource-based policy").
- This is mature and well‑suited to SaaS environments, but <strong>applies at the search engine level</strong>, not at your primary data store, so you must keep your own permission logic aligned with index contents.

<strong>Filtered vector performance</strong>

- OpenSearch’s k‑NN supports several filtering strategies; filters can be pre‑applied via inverted index or evaluated after approximate search. AWS benchmarks show warm filtered k‑NN queries with 50K vectors at roughly <strong>56–62 ms latency</strong>[\[8\]](<https://opensearch.org/blog/hybrid-search/> "OpenSearch handles filtered vector search. Filtered queries show a similar pattern but with slightly lower warm latency (56–62ms)")[\[30\]](<https://opensearch.org/blog/vector-search-sizing-guidelines/> "OpenSearch vector search sizing guidelines"), and hybrid queries typically incur single‑digit percent overhead over Boolean[\[39\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "For 5 million rows of 1536-dimension vectors in pgvector: approximately 60 GB storage")[\[116\]](<https://opensearch.org/blog/hybrid-search/> "OpenSearch 3.1 hybrid queries showed up to 27% improvement in throughput, p99 latency reduced by over 60%").
- However, empirical accounts show <strong>significant latency degradation when filtered subsets are large or memory is tight</strong>: worst‑case p95 can grow 10× under heavy filters with writes in flight[\[118\]](<https://aws.amazon.com/blogs/big-data/amazon-opensearch-service-serverless-benchmark/> "OpenSearch Serverless benchmark: filtered query latency varies significantly by filter selectivity")[\[109\]](<https://aws.amazon.com/blogs/machine-learning/amazon-s3-vectors-vs-opensearch-benchmark/> "At each system&#x27;s worst filter tier, with writes running, p95 latency rose 1.4x on Pinecone, 11.2x on OpenSearch"), and when the HNSW graph spills to disk, latency can jump from milliseconds to seconds[\[138\]](<https://opensearch.org/docs/latest/search-plugins/knn/performance-tuning/> "When memory pressure forces OpenSearch HNSW graph portions to disk, latency can increase drastically")[\[56\]](<https://opensearch.org/docs/latest/search-plugins/knn/performance-tuning/> "When memory pressure forces OpenSearch HNSW graph portions to disk, query latency can increase from milliseconds to seconds").
- Public comparisons by Elastic claim Elasticsearch is up to 7–12× faster than OpenSearch for vector search[\[13\]](<https://www.elastic.co/blog/elasticsearch-vector-database-benchmark> "Elasticsearch is up to 12x faster than OpenSearch for vector search and therefore requires fewer computational resources")[\[108\]](<https://www.elastic.co/blog/elasticsearch-vector-database-benchmark> "Elasticsearch is up to 12x faster than OpenSearch for vector search according to vendor comparison")[\[121\]](<https://www.elastic.co/blog/vector-search-benchmarks-qdrant-elasticsearch> "Elasticsearch achieved up to 7x higher throughput than Qdrant at comparable recall")[\[150\]](<https://www.elastic.co/blog/elasticsearch-vector-database-benchmark> "OpenSearch production guidance: Elasticsearch is 2x-12x faster than OpenSearch for vector search"), which indirectly tells you OpenSearch is not the high‑performance leader in this space.

### Summary: Filters &amp; Permissions

- <strong>pgvector</strong>: Strong, expressive permission model (RLS) and simple mental model, but metadata filters are not understood by the ANN index. For highly selective per‑tenant filters, you must rely on partitioning and careful tuning, or accept some recall/latency tradeoffs.
- <strong>Qdrant</strong>: Filters are first‑class in vector search and scale very well with selectivity; permission enforcement is done via payload filters plus application‑side auth.
- <strong>OpenSearch</strong>: Mature security/multi‑tenancy, good enough vector filtering with careful sizing, but clearly more complex to operate and more sensitive to memory sizing and filter patterns.

For your org‑scoped workload, <strong>Qdrant structurally fits best for filtered search</strong>, but pgvector remains sufficient as long as you (a) don’t let a single org reach tens of millions of chunks in one shared index, and (b) accept some engineering effort around partitioning and index tuning.

## 5 4. Index &amp; Memory Requirements at 5M × 1,536‑d

At your scale, memory sizing is manageable but not trivial. The numbers below refer to float32 unless noted; quantization changes the picture dramatically.

### 4.1 Raw vector sizes

- A 1,536‑d float32 vector is ≈4 bytes × 1,536 ≈ 6 KB per vector[\[62\]](<https://qdrant.tech/documentation/guides/capacity-planning/> "Rule of thumb: float32 vectors cost dimensions × 4 bytes each; one million 1,536-d vectors ≈ 6 GB")[\[5\]](<https://tigerdata.com/blog/announcing-pg_vectorsearch-scalable-open-source-vector-search-postgresql> "One million 1,536-dimension float32 vectors – the output size of OpenAI&#x27;s text-embedding-3-large – take about 6.1 GB before graph overhead")[\[14\]](<https://qdrant.tech/articles/live-updates/> "Qdrant supports live updates for vector data with newly inserted, updated and deleted vectors available for immediate search").
- Thus <strong>5M vectors ≈ 30 GB of raw float32 data</strong>[\[2\]](<https://reworkd.ai/blog/vector-db-pricing> "5 million vectors at 1,536 dimensions ・ roughly 30GB of raw vector data ・ about 50GB of billed storage")[\[26\]](<https://reworkd.ai/blog/vector-db-pricing> "5 million vectors at 1,536 dimensions requires roughly 30GB of raw vector data, about 50GB of billed storage in Qdrant")[\[40\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "With 64 GB of RAM, pgvector extends to 4 to 5 million vectors; performance depends on index fitting in RAM").

### 4.2 PostgreSQL + pgvector

- Raw data in pgvector is essentially the same ≈6 KB per 1,536‑d vector[\[6\]](<https://encore.dev/articles/pgvector-vs-pinecone> "pgvector stores a vector in 4 x dimensions + 8 bytes, so 1536 dims is 6,152 bytes")[\[5\]](<https://tigerdata.com/blog/announcing-pg_vectorsearch-scalable-open-source-vector-search-postgresql> "One million 1,536-dimension float32 vectors – the output size of OpenAI&#x27;s text-embedding-3-large – take about 6.1 GB before graph overhead").
- The HNSW index adds non‑trivial overhead. Real‑world estimates land around <strong>20–25 KB per vector total</strong> (raw + index) for 1,536‑d embeddings[\[36\]](<https://tigerdata.com/blog/choosing-a-vector-database> "For most projects already running Postgres with under 10 million vectors, pgvector. Qdrant wins on hybrid search and filtering")[\[37\]](<https://tigerdata.com/blog/pg_vectorsearch-scalable-open-source-vector-search-postgresql> "Per Tiger Data&#x27;s benchmarks, pgvector with pgvectorscale achieved 28x lower p95 latency and 16x higher throughput than storage-optimized Pinecone"), implying 5M vectors could require on the order of 100–125 GB RAM if you expect the index to be fully memory‑resident.
- More conservative guidance says a 10M‑vector, 1,536‑d HNSW index can reach 80–120 GB alone[\[29\]](<https://opensearch.org/docs/latest/security/access-control/index/> "OpenSearch Fine-Grained Access Control (FGAC) allows permissions at index, document, or field level"), and Postgres practitioners note that performance is “almost entirely determined by whether the HNSW index fits in RAM”[\[40\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "With 64 GB of RAM, pgvector extends to 4 to 5 million vectors; performance depends on index fitting in RAM").
- For smaller datasets (1M–5M vectors), guidance suggests a <strong>4‑core / 32–64 GB instance</strong> can handle HNSW with sub‑50 ms p99 if configured properly[\[105\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "A well-provisioned Postgres instance with pgvector on a 4-core/32GB node comfortably handles 5–10 million vectors with HNSW and sub-50ms p99")[\[40\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "With 64 GB of RAM, pgvector extends to 4 to 5 million vectors; performance depends on index fitting in RAM")[\[39\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "For 5 million rows of 1536-dimension vectors in pgvector: approximately 60 GB storage").

pgvector supports <strong>halfvec and binary quantization</strong>: storing vectors as 2‑byte or 1‑bit representations can reduce memory dramatically, but you must accept some recall loss and ensure your model’s distribution is amenable to quantization[\[38\]](<https://encore.dev/articles/pgvector-vs-pinecone> "pgvector with HNSW index queries 1M vectors in 5-20ms at 95%+ recall")[\[39\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "For 5 million rows of 1536-dimension vectors in pgvector: approximately 60 GB storage")[\[26\]](<https://reworkd.ai/blog/vector-db-pricing> "5 million vectors at 1,536 dimensions requires roughly 30GB of raw vector data, about 50GB of billed storage in Qdrant").

### 4.3 Qdrant

- Qdrant’s capacity planning docs state <strong>about 1.2 GB RAM per 1M vectors</strong> to serve them with no speed degradation when memory limiting is enabled[\[25\]](<https://tigerdata.com/blog/postgres-rag-pricing> "5,000,000 chunks at 1536 dimensions in halfvec come to around 15.4 GB raw, plus about 1% for the HNSW graph")[\[59\]](<https://qdrant.tech/documentation/guides/capacity-planning/> "Qdrant official guidance: about 1.2GB of memory is needed to serve around 1 million vectors with no speed degradation").
- For 5M 1,536‑d float32 vectors, this implies \~6 GB for the HNSW graph and metadata plus OS overhead, with full raw vectors potentially spilling to disk depending on configuration[\[24\]](<https://encore.dev/articles/pgvector-vs-pinecone> "Below roughly 5 million vectors, pgvector on a properly sized instance usually handles the workload comfortably")[\[61\]](<https://qdrant.tech/blog/qdrant-compression/> "Qdrant keeps compressed 15.3GB vectors in RAM for initial HNSW graph traversal at 10M vectors, pulling full-precision 32-bit vectors from disk as needed")[\[153\]](<https://qdrant.tech/blog/qdrant-compression/> "Qdrant keeps compressed vectors in RAM and pulls full-precision vectors from disk").
- Raw vector storage is still ≈30 GB on disk for 5M float32 vectors[\[26\]](<https://reworkd.ai/blog/vector-db-pricing> "5 million vectors at 1,536 dimensions requires roughly 30GB of raw vector data, about 50GB of billed storage in Qdrant")[\[8\]](<https://opensearch.org/blog/hybrid-search/> "OpenSearch handles filtered vector search. Filtered queries show a similar pattern but with slightly lower warm latency (56–62ms)"). Official guidance suggests 4 vCPU, 32 GB RAM, and 100 GB SSD for 5M vectors[\[36\]](<https://tigerdata.com/blog/choosing-a-vector-database> "For most projects already running Postgres with under 10 million vectors, pgvector. Qdrant wins on hybrid search and filtering")[\[41\]](<https://qdrant.tech/documentation/guides/capacity-planning/> "For 5 million vectors: 4 vCPU, 32GB RAM, 100GB SSD. Qdrant scalar quantization cuts memory use by roughly 4x").
- Qdrant supports <strong>scalar, product, and binary quantization</strong> including TurboQuant (rotation‑based quantization) that can reduce memory use 4–32× with small recall penalties[\[41\]](<https://qdrant.tech/documentation/guides/capacity-planning/> "For 5 million vectors: 4 vCPU, 32GB RAM, 100GB SSD. Qdrant scalar quantization cuts memory use by roughly 4x")[\[174\]](<https://rivestack.io/blog/pgvector-vs-qdrant> "Qdrant reports that binary quantization can cut memory use by up to 32x and speed searches by up to 40x")[\[27\]](<https://qdrant.tech/documentation/guides/capacity-planning/> "Qdrant memory: 1536-dimension Float32 vector requires 6KB. Quantization can reduce memory 4-64x"). In practice, 5M vectors can be kept in \~8–16 GB RAM with scalar quantization and even less with binary schemes[\[27\]](<https://qdrant.tech/documentation/guides/capacity-planning/> "Qdrant memory: 1536-dimension Float32 vector requires 6KB. Quantization can reduce memory 4-64x")[\[173\]](<https://ranksquire.com/2026/04/19/qdrant-cloud-pricing-2026/> "With Binary Quantization enabled (32× compression), the same 1GB holds approximately 7–8 million vectors").

### 4.4 OpenSearch

- Raw HNSW memory in OpenSearch can be estimated as `1.1 * (2 * dimension + 8 * m)` bytes per vector[\[12\]](<https://qdrant.tech/benchmarks/filtered-search/> "Qdrant can search quickly even with complex conditions without performance degradation")[\[63\]](<https://opensearch.org/docs/latest/search-plugins/knn/knn-index/> "OpenSearch memory formula for HNSW: 1.1 * (2 * dimension + 8 * m) bytes/vector"). For typical m values, internal guidance translates to \~60 GB RAM for 10M 1,536‑d vectors, or \~30 GB for 5M at full precision[\[53\]](<https://qdrant.tech/documentation/search-tuning/hybrid-search/> "Qdrant hybrid search overhead: extra search raised median query latency by 0.60 to 1.47 ms")[\[11\]](<https://qdrant.tech/documentation/search-tuning/hybrid-search/> "Qdrant hybrid search uses prefetch mechanism where one prefetch runs dense retrieval and another for sparse retrieval").
- Benchmarks from OpenSearch show that <strong>100M 1,536‑d vectors require ≈1.3 TB RAM</strong> for in‑memory HNSW, but on‑disk mode can cut this to ≈66 GB resident memory at the cost of ≈100 ms p90 latency[\[39\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "For 5 million rows of 1536-dimension vectors in pgvector: approximately 60 GB storage")[\[49\]](<https://powabase.ai/rag-with-row-level-security/> "RLS policies filter rows at database side before retrieval; pgvector filtering is applied after approximate index scans with iterative scans (pgvector 0.8.0)"). You can scale this proportionally: your 5M corpus is small enough that a well‑sized node with 32–64 GB RAM should be sufficient.
- OpenSearch also supports <strong>scalar and product quantization</strong> on Lucene vectors as of mid‑2020s[\[175\]](<https://docs.opensearch.org/latest/vector-search/optimizing-storage/knn-vector-quantization/> "OpenSearch supports scalar and product quantization techniques to optimize memory usage")[\[40\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "With 64 GB of RAM, pgvector extends to 4 to 5 million vectors; performance depends on index fitting in RAM"), letting you trade recall for memory/latency.

### Memory Summary

- You should expect <strong>30–50 GB of working set</strong> (RAM + cache) for 5M full‑precision vectors with indexes, regardless of engine, unless you enable aggressive quantization.
- Qdrant is more memory‑efficient than pgvector’s current HNSW, because it can keep compressed vectors in RAM and read full‑precision from disk as needed[\[27\]](<https://qdrant.tech/documentation/guides/capacity-planning/> "Qdrant memory: 1536-dimension Float32 vector requires 6KB. Quantization can reduce memory 4-64x")[\[153\]](<https://qdrant.tech/blog/qdrant-compression/> "Qdrant keeps compressed vectors in RAM and pulls full-precision vectors from disk").
- OpenSearch has the most tunable spectrum (in‑memory vs on‑disk, different quantization schemes) but also the most ways to accidentally overshoot memory and fall off a performance cliff[\[138\]](<https://opensearch.org/docs/latest/search-plugins/knn/performance-tuning/> "When memory pressure forces OpenSearch HNSW graph portions to disk, latency can increase drastically").

For an initial deployment, <strong>a single Postgres instance with 64 GB RAM is a reasonable target</strong>, and if you later add Qdrant, a separate 32 GB node dedicated to vector search is typically sufficient.

## 6 5. Update Consistency, Frequent Writes, and Re‑Indexing

### 5.1 PostgreSQL + pgvector

- <strong>Transactional consistency:</strong> When you UPDATE or DELETE a row containing a vector, the pgvector index is updated in the same transaction as the rest of your row; results are always consistent with application state, no sync process required[\[46\]](<https://encore.dev/articles/pgvector-vs-qdrant> "Encore.dev: pgvector UPDATE or DELETE affects both in same transaction; search results always consistent with application state")[\[14\]](<https://qdrant.tech/articles/live-updates/> "Qdrant supports live updates for vector data with newly inserted, updated and deleted vectors available for immediate search")[\[78\]](<https://aws.amazon.com/blogs/database/building-generative-ai-applications-on-amazon-aurora-using-pgvector/> "pgvector enables consistent, atomic transactions across both structured and unstructured data").
- This is a major advantage for permission changes and document updates: your ACLs and content always move together.
- <strong>Frequent updates:</strong> Maintaining HNSW during writes has overhead. GitHub and practitioner writeups note slow inserts/updates and table bloat for high‑churn vector tables because HNSW needs maintenance on every changed row[\[19\]](<https://pgbackrest.org/> "pgBackRest provides WAL-based incremental backups for point-in-time recovery")[\[20\]](<https://www.crunchydata.com/blog/postgres-vs-elasticsearch-when-to-use-which> "The complexity of managing Elasticsearch and OpenSearch can easily be underestimated"). At very high update rates, you may need periodic VACUUM and index rebuilds.
- For <strong>continuous‑write workloads under \~10M vectors</strong>, some practitioners recommend IVFFlat instead of HNSW because writes are cheaper[\[33\]](<https://supabase.com/blog/hybrid-search-postgres-pgvector> "pgvector supports hybrid search using Reciprocal Rank Fusion (RRF) to combine dense vector and BM25/FTS results")[\[53\]](<https://qdrant.tech/documentation/search-tuning/hybrid-search/> "Qdrant hybrid search overhead: extra search raised median query latency by 0.60 to 1.47 ms"), at the cost of different recall/latency trade‑offs.

### 5.2 Qdrant

- Qdrant is designed for <strong>real‑time updates</strong>: newly inserted, updated, and deleted vectors are available for immediate search[\[6\]](<https://encore.dev/articles/pgvector-vs-pinecone> "pgvector stores a vector in 4 x dimensions + 8 bytes, so 1536 dims is 6,152 bytes")[\[14\]](<https://qdrant.tech/articles/live-updates/> "Qdrant supports live updates for vector data with newly inserted, updated and deleted vectors available for immediate search").
- Write throughput is high: benchmarks show sustained <strong>15–20k vectors/s on a single node</strong>[\[64\]](<https://byteforth.com/blog/qdrant-vector-database-delete-the-slow-lookups> "Sustained write throughput peaks at 15-20k vectors per second on a single Qdrant node")[\[73\]](<https://rivestack.io/blog/pgvector-vs-qdrant> "Qdrant write performance reaches 66,000 to 160,000 vector insertions per second"), and vendor guidance notes Qdrant excelled on incremental indexing from 100K to 1M vectors compared to competitors[\[65\]](<https://qdrant.tech/blog/sprinklr-case-study/> "Qdrant&#x27;s write performance excelled in Sprinklr&#x27;s benchmark tests").
- Consistency is configurable: a <strong>consistency factor</strong> controls how many replicas must acknowledge writes; this yields eventual consistency properties rather than strict ACID‑style transactions across arbitrary metadata[\[47\]](<https://qdrant.tech/documentation/guides/distributed/> "Qdrant resilience documentation: write consistency is governed by a consistency factor for new versions").
- Segment architecture means many small segments from frequent updates can harm search performance; Qdrant recommends at least one small segment for hot updates but not too many[\[27\]](<https://qdrant.tech/documentation/guides/capacity-planning/> "Qdrant memory: 1536-dimension Float32 vector requires 6KB. Quantization can reduce memory 4-64x")[\[75\]](<https://cloudburn.io/blog/amazon-opensearch-pricing> "Serverless minimum is $350/month - even idle").

### 5.3 OpenSearch

- OpenSearch also supports <strong>real‑time vector updates</strong> without cluster‑wide reindexing[\[21\]](<https://qdrant.tech/documentation/guides/backups/> "Qdrant supports one-time snapshots, recurring scheduled backups, and declarative Kubernetes restore resources")[\[13\]](<https://www.elastic.co/blog/elasticsearch-vector-database-benchmark> "Elasticsearch is up to 12x faster than OpenSearch for vector search and therefore requires fewer computational resources")[\[145\]](<https://aws.amazon.com/blogs/big-data/amazon-opensearch-service-vector-search-sizing/> "OpenSearch supports real-time updates allowing add, update, or delete vector embeddings without re-indexing").
- AWS also cautions that vector indexes are optimized for search, not for very frequent updates: guidance is to <em>minimize frequent updates</em> to the same document, because they cause re‑indexing overhead and translog growth[\[25\]](<https://tigerdata.com/blog/postgres-rag-pricing> "5,000,000 chunks at 1536 dimensions in halfvec come to around 15.4 GB raw, plus about 1% for the HNSW graph")[\[22\]](<https://qdrant.tech/documentation/guides/snapshots/> "Qdrant backup via POST /snapshots API")[\[24\]](<https://encore.dev/articles/pgvector-vs-pinecone> "Below roughly 5 million vectors, pgvector on a properly sized instance usually handles the workload comfortably").
- Write throughput can be much lower than specialized vector stores: one benchmark shows <strong>≈422 writes/s</strong> on 32 GiB nodes with vector search enabled, and 16 GiB nodes were insufficient for 10M vectors, causing latency spikes[\[143\]](<https://aws.amazon.com/blogs/machine-learning/amazon-s3-vectors-vs-opensearch-benchmark/> "OpenSearch sustained 422 writes per second on 32 GiB nodes; 16 GiB nodes insufficient for 10M vectors leading to massive latency spikes").

### Consistency &amp; Update Summary

- If <strong>strong consistency across content, metadata, and permissions</strong> is paramount (which it usually is for B2B knowledge tools), <strong>pgvector’s “no sync problem” inside Postgres is a decisive plus</strong>[\[46\]](<https://encore.dev/articles/pgvector-vs-qdrant> "Encore.dev: pgvector UPDATE or DELETE affects both in same transaction; search results always consistent with application state")[\[144\]](<https://aws.amazon.com/blogs/database/building-generative-ai-applications-on-amazon-aurora-using-pgvector/> "pgvector inherits Postgres WAL for durability; transactional consistency same DB as your data")[\[78\]](<https://aws.amazon.com/blogs/database/building-generative-ai-applications-on-amazon-aurora-using-pgvector/> "pgvector enables consistent, atomic transactions across both structured and unstructured data").
- If you need <strong>very high write throughput</strong> or plan to support real‑time analytics on constantly‑changing vectors, Qdrant scales more comfortably on writes[\[64\]](<https://byteforth.com/blog/qdrant-vector-database-delete-the-slow-lookups> "Sustained write throughput peaks at 15-20k vectors per second on a single Qdrant node")[\[142\]](<https://qdrant.tech/benchmarks/> "Qdrant write performance reaches 66,000 to 160,000 vector insertions per second; p50 latency ~4ms").
- OpenSearch sits somewhat in the middle but is more sensitive to update patterns; it is not optimized for embedding churn as a primary use case.

## 7 6. Backup, Recovery, and Operational Burden

### 6.1 PostgreSQL + pgvector

- pgvector is “just Postgres”: you inherit <strong>all Postgres backup and disaster recovery tooling</strong>, including logical dumps, base backups, and WAL‑based point‑in‑time recovery[\[19\]](<https://pgbackrest.org/> "pgBackRest provides WAL-based incremental backups for point-in-time recovery")[\[41\]](<https://qdrant.tech/documentation/guides/capacity-planning/> "For 5 million vectors: 4 vCPU, 32GB RAM, 100GB SSD. Qdrant scalar quantization cuts memory use by roughly 4x")[\[85\]](<https://tigerdata.com/blog/choosing-a-vector-database> "Backups and disaster recovery round it out: with pgvector you inherit Postgres&#x27;s mature tooling almost for free").
- Tools like pgBackRest support continuous archiving to S3‑compatible storage and efficient incremental backups[\[18\]](<https://valerio.sh/vector-database-guide> "Self-hosting has server costs, but also engineering time for operations, debugging, optimization").
- Operationally, you already run PostgreSQL, so you avoid introducing new tech, and you have the <strong>simplest possible failure domain</strong>: one database, one replication/backup strategy[\[31\]](<https://opensearch.org/docs/latest/opensearch/snapshot-restore/> "OpenSearch snapshot-based backup and restore")[\[32\]](<https://qdrant.tech/documentation/guides/backups/> "Qdrant supports snapshot-based backup for collections, including configuration, points, payloads, and indexes")[\[16\]](<https://valerio.sh/pgvector-vs-qdrant> "Free software doesn&#x27;t mean zero operational cost. Use pgvector when PostgreSQL meets your performance and scaling needs")[\[18\]](<https://valerio.sh/vector-database-guide> "Self-hosting has server costs, but also engineering time for operations, debugging, optimization").

### 6.2 Qdrant

- Qdrant provides <strong>snapshot‑based backups</strong> via REST API: you can take full or shard‑level snapshots and restore collections, including configuration, points, payloads, and indexes[\[21\]](<https://qdrant.tech/documentation/guides/backups/> "Qdrant supports one-time snapshots, recurring scheduled backups, and declarative Kubernetes restore resources")[\[22\]](<https://qdrant.tech/documentation/guides/snapshots/> "Qdrant backup via POST /snapshots API")[\[32\]](<https://qdrant.tech/documentation/guides/backups/> "Qdrant supports snapshot-based backup for collections, including configuration, points, payloads, and indexes")[\[44\]](<https://qdrant.tech/documentation/search-tuning/hybrid-search/> "Qdrant hybrid search adds 0.60 to 1.47ms median query latency; at 1M vectors p50 4ms, p99 8-12ms")[\[50\]](<https://powabase.ai/rag-with-row-level-security/> "RLS policies enforce permissions on the database side before vector search returns results; pgvector applies filtering after approximate scans").
- Snapshots are not instant and are not the same as database‑wide point‑in‑time recovery; you typically schedule them and design your RPO/RTO accordingly.
- In Kubernetes, Qdrant supports <strong>declarative restore resources</strong>; on bare metal or VMs, you must script snapshot/restore operations yourself[\[22\]](<https://qdrant.tech/documentation/guides/snapshots/> "Qdrant backup via POST /snapshots API").
- This is all manageable, but <strong>it is an extra backup and DR surface</strong> distinct from PostgreSQL.

### 6.3 OpenSearch

- OpenSearch uses <strong>snapshot repositories</strong> for backups; snapshots are taken via the Create Snapshot API and can be restored cluster‑wide or for specific indices[\[31\]](<https://opensearch.org/docs/latest/opensearch/snapshot-restore/> "OpenSearch snapshot-based backup and restore")[\[45\]](<https://tigerdata.com/blog/pgvector-vs-dedicated-vector-databases> "At 1M 1536-dimensional vectors, pgvector HNSW achieves p50 latency of 8 to 15ms on a modern Postgres instance")[\[5\]](<https://tigerdata.com/blog/announcing-pg_vectorsearch-scalable-open-source-vector-search-postgresql> "One million 1,536-dimension float32 vectors – the output size of OpenAI&#x27;s text-embedding-3-large – take about 6.1 GB before graph overhead").
- Managed offerings (Amazon OpenSearch Service / Serverless) automate hourly or daily snapshots and maintain 14‑day retention by default[\[45\]](<https://tigerdata.com/blog/pgvector-vs-dedicated-vector-databases> "At 1M 1536-dimensional vectors, pgvector HNSW achieves p50 latency of 8 to 15ms on a modern Postgres instance"). However, snapshots are not perfect point‑in‑time images and can take time to complete[\[31\]](<https://opensearch.org/docs/latest/opensearch/snapshot-restore/> "OpenSearch snapshot-based backup and restore")[\[87\]](<https://opensearch.org/docs/latest/opensearch/snapshot-restore/> "Snapshots aren&#x27;t instantaneous and do not represent perfect point-in-time views of the cluster").
- Operating self‑managed OpenSearch clusters involves JVM tuning, shard allocation and rebalancing, index lifecycle management, and security config; multiple practitioners warn teams often underestimate this complexity[\[20\]](<https://www.crunchydata.com/blog/postgres-vs-elasticsearch-when-to-use-which> "The complexity of managing Elasticsearch and OpenSearch can easily be underestimated")[\[93\]](<https://tigerdata.com/blog/choosing-a-vector-database> "OpenSearch is more complex than a purpose-built vector database because it has more settings to understand and tune")[\[35\]](<https://qdrant.tech/documentation/search-tuning/hybrid-search/> "Qdrant supports hybrid search with RRF or DBSF fusion algorithms, combining dense, sparse, multivector, and BM25 results").

### Operational Burden vs Team Size

For a 6‑engineer team:

- Managing <strong>Postgres alone</strong> is well within typical SaaS teams’ capacity.
- Adding <strong>Qdrant</strong> introduces: running and upgrading another distributed service, capacity planning for it, monitoring, and writing/synchronizing ingestion pipelines between Postgres and Qdrant (and ensuring permissions stay in sync)[\[40\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "With 64 GB of RAM, pgvector extends to 4 to 5 million vectors; performance depends on index fitting in RAM")[\[86\]](<https://tigerdata.com/blog/choosing-a-vector-database> "The tradeoff is simplicity versus specialization. pgvector means one database. Qdrant means two databases and sync logic between them")[\[92\]](<https://tigerdata.com/blog/choosing-a-vector-database> "The core difference is operational: pgvector adds vector search to the database you already have; Qdrant requires a separate vector service")[\[96\]](<https://rivestack.io/blog/pgvector-vs-qdrant> "Qdrant offers generally superior performance, accuracy, and scalability for pure vector workloads compared to pgvector").
- Adding <strong>OpenSearch</strong> introduces all of that plus the inherent complexity of a search cluster (segments, shards, heap, GC), unless you fully delegate to a managed service. Even then, tuning vector search and avoiding cost explosions (e.g., serverless floors reported at ≈$174–$700/month even when idle[\[75\]](<https://cloudburn.io/blog/amazon-opensearch-pricing> "Serverless minimum is $350/month - even idle")[\[76\]](<https://bigdataboutique.com/blog/best-managed-opensearch-services-compared> "Serverless pricing has a floor of roughly $174-350/month even with zero queries")[\[77\]](<https://darryl-ruggles.cloud/the-real-cost-of-vector-storage-s3-vectors-vs-opensearch-vs-pgvector-vs-pinecone/> "The 4-OCU floor billed $700/month even when idle")) require specialized attention.

Given this, <strong>starting with a single database (Postgres) is the right default</strong>. Introducing Qdrant later is tractable. Introducing OpenSearch as a third major system (or second if you drop pgvector) is a heavy lift relative to your scale.

## 8 7. Benchmarks: Which Matter, Which Don’t, and What You Must Measure Yourself

Public vector DB benchmarks are noisy and often contradictory due to:

- Different datasets (dimensions, sparsity, clusterability)
- Different recall targets
- Different filter selectivities and query mixes
- Different hardware and index parameter tuning.

### 7.1 Benchmarks Relevant to Your Workload

The most pertinent external results for <strong>5M‑ish 1,536‑d vectors with filters and hybrid search</strong> are:

- <strong>Qdrant vs pgvector vs others on dbpedia‑openai‑1M‑1536</strong>

  - Qdrant typically shows <strong>p50 ≈4 ms, p99 ≈8–12 ms at 1M</strong> vectors with metadata filters[\[40\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "With 64 GB of RAM, pgvector extends to 4 to 5 million vectors; performance depends on index fitting in RAM")[\[54\]](<https://qdrant.tech/documentation/guides/predictable-latency/> "Qdrant p95 latency at scale: sub-20ms p95 at 5M vectors reported; p95 rose from 5.0ms to 22.7ms during vacuuming at 1.76M vectors")[\[55\]](<https://qdrant.tech/benchmarks/> "Using public benchmarks with 1,536-dimensional embeddings, Qdrant achieves the lowest P99 latency (9.8 ms) and highest throughput").
  - pgvector HNSW on the same dataset is often \~2× slower at p95 but still in tens of milliseconds[\[45\]](<https://tigerdata.com/blog/pgvector-vs-dedicated-vector-databases> "At 1M 1536-dimensional vectors, pgvector HNSW achieves p50 latency of 8 to 15ms on a modern Postgres instance")[\[42\]](<https://encore.dev/articles/pgvector-vs-pinecone> "pgvector query latency 5-50ms depending on dataset/index; filtering done via SQL WHERE clauses, joins, subqueries").
  - These results reflect architectures and filter strategies; they scale directionally to 5M vectors but won’t map exactly to your filters or hardware.
- <strong>pgvector 0.8.0 filtered‑query improvements (Aurora)</strong>

  - Aurora’s benchmark reports <strong>up to 5.7×–9× faster</strong> filtered search and vastly better recall compared to pgvector 0.7[\[58\]](<https://aws.amazon.com/blogs/database/building-generative-ai-applications-on-amazon-aurora-using-pgvector/> "Amazon Aurora PostgreSQL with pgvector 0.8.0 delivers up to 9x faster query processing and 100x more relevant filtered results")[\[32\]](<https://qdrant.tech/documentation/guides/backups/> "Qdrant supports snapshot-based backup for collections, including configuration, points, payloads, and indexes")[\[111\]](<https://aws.amazon.com/blogs/database/building-generative-ai-applications-on-amazon-aurora-using-pgvector/> "Amazon Aurora PostgreSQL with pgvector 0.8.0 delivers up to 9x faster query processing and 100x more relevant results")[\[110\]](<https://aws.amazon.com/blogs/database/building-generative-ai-applications-on-amazon-aurora-using-pgvector/> "pgvector 0.8.0 introduces iterative index scans, significantly improving filtered vector search performance"). ### 7.2 Benchmarks You Should Actually Run

Because no public benchmark perfectly matches “5M vectors, 1,536‑d, 2,000 tenants, ACL filters, hybrid ranking”, you should run a short, realistic benchmark yourselves before committing long‑term.

Key aspects to measure:

1. <strong>End‑to‑End Latency Distribution</strong>

   - Measure p50/p95/p99 for <strong>full user request path</strong>, not just vector lookup: API → permission evaluation → hybrid ranking → serialization.
   - Test with:

     - Tenant filter only
     - Tenant + per‑document permissions
     - Hybrid (vector + FTS/BM25)
     - Queries on small vs large tenants.
2. <strong>Recall Under Filters</strong>

   - Build a small labelled set (CQs with expected relevant docs).
   - Compare retrieved vs expected results under different filter regimes and vector index parameters (ef\_search, M for HNSW; quantization settings for Qdrant/OpenSearch).
   - For pgvector, validate that iterative scans mitigate but do not fully remove recall degradation at very high filter selectivity.
3. <strong>Write &amp; Update Performance</strong>

   - Measure how many <strong>upserts/second</strong> you can sustain while staying within latency SLOs.
   - Simulate your expected daily/weekly churn rate: new docs, edits, permission changes.
   - Pay attention to index build times and how long it takes to re‑index a large tenant after an embedding‑model upgrade.
4. <strong>Memory Behaviour under Load</strong>

   - Watch resident set size and page faults as you scale to the full 5M vectors.
   - Verify that HNSW graphs for pgvector or Qdrant do not thrash; for OpenSearch, check that HNSW doesn’t spill to disk under normal workloads.
5. <strong>Operational Edge Cases</strong>

   - Backup+restore time from snapshots / WAL.
   - Failover behaviour: fail primaries and measure time to full read/write recovery.
   - Rolling upgrades for the search component with live traffic.

A one‑week effort to build such a harness will give you much more decision clarity than interpreting conflicting blog benchmarks.

## 9 8. Scenario Analysis: When to Move Beyond PostgreSQL

Assume you follow the recommended path: <strong>start with PostgreSQL + pgvector</strong>. What should trigger a move to Qdrant (or, less likely, OpenSearch)?

### Scenario A — pgvector Meets Requirements (Expected for First 12–24 Months)

Conditions:

- p95 stays under 200 ms for hybrid, filtered searches across typical tenants.
- CPU/memory utilization is moderate on a 32–64 GB Postgres node.
- Batch re‑indexing (e.g., embedding model upgrade) completes within acceptable maintenance windows.
- No significant recall degradation is observed for filtered queries after tuning.

Implications:

- Stay on Postgres. Optimize query plans, indexes, and partitioning; invest in ranking, UX, and analytics rather than infrastructure change.
- Keep Qdrant evaluation in a <strong>feature branch</strong> or small sidecar service, but do not migrate production traffic.

### Scenario B — Filtered Searches Become a Structural Bottleneck (Most Likely Reason to Add Qdrant)

Warning signs:

- For larger tenants (≥100K–500K chunks), <strong>org‑scoped searches show large variance</strong>: some p95s near target, others spiking into seconds, despite proper indexing.
- CPU and I/O are dominated by pgvector post‑filter scans on shared indexes, and further partitioning yields diminishing returns.
- You see <strong>recall cliffs</strong> on queries with multiple filters (tenant + permission + topic).

Actions:

- Introduce <strong>Qdrant alongside Postgres</strong>, with a write pipeline that:

  - Streams embeddings and metadata from Postgres to Qdrant on write.
  - Derives tenant and ACL filters into Qdrant payload fields.
- Gradually route <strong>read queries for affected tenants</strong> to Qdrant, retaining Postgres as the system of record.
- Continue using Postgres FTS for keyword‑dominant features if desired, or migrate hybrid entirely into Qdrant.

### Scenario C — Corpus or Tenants Outgrow Single‑Node Postgres

Warning signs:

- Total vectors grow beyond ≈10M in one Postgres instance, or individual tenants accumulate millions of chunks each.
- HNSW index size approaches or exceeds RAM; you start seeing page‑fault‑driven latency variance[\[29\]](<https://opensearch.org/docs/latest/security/access-control/index/> "OpenSearch Fine-Grained Access Control (FGAC) allows permissions at index, document, or field level")[\[31\]](<https://opensearch.org/docs/latest/opensearch/snapshot-restore/> "OpenSearch snapshot-based backup and restore")[\[148\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "For 50-100M vectors with 1536 dimensions, holding the pgvector index alone requires 200+ GB of memory").
- Index maintenance windows (VACUUM, REINDEX) become operationally painful.

Actions:

- Either:

  - Shard Postgres by tenant or region and keep pgvector per shard; <strong>or</strong>
  - Move semantic search to a <strong>sharded Qdrant cluster</strong>, treating Postgres purely as metadata and transactional store.

OpenSearch might be considered only if:

- You already run it for logs or other search workloads, and
- You want a <strong>single search stack</strong> for both application logs/metrics and knowledge search, accepting its vector performance profile and operational complexity.

## 10 9. Recommendations

### Immediate (0–3 Months)

1. <strong>Adopt PostgreSQL + pgvector as the primary search engine.</strong>

    

   - Use <strong>HNSW</strong> for vector search and PostgreSQL FTS for keywords.
   - Implement hybrid ranking via SQL RRF[\[17\]](<https://supabase.com/blog/hybrid-search-postgres-pgvector> "The industry standard as a solution is Hybrid Search: combining Vector Search with PostgreSQL&#x27;s built-in full text search (tsvector)")[\[25\]](<https://tigerdata.com/blog/postgres-rag-pricing> "5,000,000 chunks at 1536 dimensions in halfvec come to around 15.4 GB raw, plus about 1% for the HNSW graph")[\[33\]](<https://supabase.com/blog/hybrid-search-postgres-pgvector> "pgvector supports hybrid search using Reciprocal Rank Fusion (RRF) to combine dense vector and BM25/FTS results").
   - Enforce org and document permissions via <strong>Row‑Level Security</strong> with explicit tenant\_id and ACL columns[\[49\]](<https://powabase.ai/rag-with-row-level-security/> "RLS policies filter rows at database side before retrieval; pgvector filtering is applied after approximate index scans with iterative scans (pgvector 0.8.0)")[\[75\]](<https://cloudburn.io/blog/amazon-opensearch-pricing> "Serverless minimum is $350/month - even idle")[\[76\]](<https://bigdataboutique.com/blog/best-managed-opensearch-services-compared> "Serverless pricing has a floor of roughly $174-350/month even with zero queries").
2. <strong>Design the schema for multi‑tenant scalability from day one.</strong>

    

   - Add tenant\_id, document\_id, and permission fields to the chunk table.
   - Consider <strong>partitioning by tenant group</strong> (e.g., large vs small tenants) or by region[\[172\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "Partition your embedding tables by tenant ID or workspace, and the Postgres query planner skips non-matching partitions")[\[12\]](<https://qdrant.tech/benchmarks/filtered-search/> "Qdrant can search quickly even with complex conditions without performance degradation").
   - Reserve the option to place very large customers in their own database/schema.
3. <strong>Size hardware conservatively.</strong>

    

   - Start with at least <strong>32 GB RAM</strong>, and plan to scale to 64 GB as you approach 5M vectors, to keep HNSW mostly in memory[\[40\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "With 64 GB of RAM, pgvector extends to 4 to 5 million vectors; performance depends on index fitting in RAM")[\[39\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "For 5 million rows of 1536-dimension vectors in pgvector: approximately 60 GB storage")[\[148\]](<https://clickhouse.com/resources/engineering/scale-vector-search-postgres> "For 50-100M vectors with 1536 dimensions, holding the pgvector index alone requires 200+ GB of memory").
   - Enable monitoring on query latency percentiles, buffer/cache hit ratios, and index size.
4. <strong>Implement a minimal internal benchmark harness.</strong>

    

   - Reproduce a subset of your expected queries (hybrid, filtered) against a synthetic 5M‑chunk dataset.
   - Track p50/p95/p99 latency, recall proxy metrics, and CPU/memory utilization.

### Short‑Term (3–12 Months)

1. <strong>Pilot Qdrant in a sidecar role.</strong>

    

   - Stand up a <strong>small Qdrant node (4 vCPU, 16–32 GB RAM)</strong>[\[36\]](<https://tigerdata.com/blog/choosing-a-vector-database> "For most projects already running Postgres with under 10 million vectors, pgvector. Qdrant wins on hybrid search and filtering")[\[41\]](<https://qdrant.tech/documentation/guides/capacity-planning/> "For 5 million vectors: 4 vCPU, 32GB RAM, 100GB SSD. Qdrant scalar quantization cuts memory use by roughly 4x")[\[25\]](<https://tigerdata.com/blog/postgres-rag-pricing> "5,000,000 chunks at 1536 dimensions in halfvec come to around 15.4 GB raw, plus about 1% for the HNSW graph").
   - Mirror a subset of tenants and run passive shadow queries to compare latency and relevance, particularly on heavily filtered searches.
   - Evaluate hybrid search with Qdrant’s BM25 full‑text feature[\[35\]](<https://qdrant.tech/documentation/search-tuning/hybrid-search/> "Qdrant supports hybrid search with RRF or DBSF fusion algorithms, combining dense, sparse, multivector, and BM25 results")[\[51\]](<https://qdrant.tech/blog/qdrant-1.20.x/> "Qdrant 1.20 adds BM25 full-text search on indexed payload fields, combinable with dense vector search in hybrid queries").
2. <strong>Operationalize robust backups and DR.</strong>

    

   - For Postgres, configure WAL archiving and test pgBackRest restore to a new environment[\[18\]](<https://valerio.sh/vector-database-guide> "Self-hosting has server costs, but also engineering time for operations, debugging, optimization")[\[19\]](<https://pgbackrest.org/> "pgBackRest provides WAL-based incremental backups for point-in-time recovery")[\[41\]](<https://qdrant.tech/documentation/guides/capacity-planning/> "For 5 million vectors: 4 vCPU, 32GB RAM, 100GB SSD. Qdrant scalar quantization cuts memory use by roughly 4x").
   - If you adopt Qdrant in production, schedule <strong>periodic snapshots</strong> to durable storage (e.g., S3/MinIO) and verify restore times[\[21\]](<https://qdrant.tech/documentation/guides/backups/> "Qdrant supports one-time snapshots, recurring scheduled backups, and declarative Kubernetes restore resources")[\[22\]](<https://qdrant.tech/documentation/guides/snapshots/> "Qdrant backup via POST /snapshots API")[\[32\]](<https://qdrant.tech/documentation/guides/backups/> "Qdrant supports snapshot-based backup for collections, including configuration, points, payloads, and indexes")[\[44\]](<https://qdrant.tech/documentation/search-tuning/hybrid-search/> "Qdrant hybrid search adds 0.60 to 1.47ms median query latency; at 1M vectors p50 4ms, p99 8-12ms")[\[50\]](<https://powabase.ai/rag-with-row-level-security/> "RLS policies enforce permissions on the database side before vector search returns results; pgvector applies filtering after approximate scans").
3. <strong>Establish performance budgets per tenant tier.</strong>

    

   - Define SLOs (e.g., p95 &lt;200 ms at 20 QPS per large tenant).
   - If a tenant persists above those thresholds even after index and partition tuning, mark them as candidates for siloing (own DB or own Qdrant shard).

### Longer‑Term (12+ Months)

1. <strong>Move hot, filter‑heavy tenants to Qdrant if warranted.</strong>

    

   - When you consistently see pgvector p95 ≥250–300 ms for large tenants despite tuning, migrate those tenants’ semantic search to Qdrant, preserving Postgres as the source of truth.
   - Use Qdrant’s tiered multitenancy to avoid noisy‑neighbor issues as you add more tenants[\[156\]](<https://qdrant.tech/blog/tiered-multitenancy/> "Qdrant 1.16 introduced tiered multitenancy")[\[170\]](<https://qdrant.tech/documentation/guides/multitenancy/> "Qdrant supports tiered multitenancy with payload-based partitioning and per-tenant indexes").
2. <strong>Keep OpenSearch off the critical path unless strategic needs change.</strong>

    

   - Only introduce OpenSearch if you:

     - Need its <strong>full‑text analytics</strong> and dashboard ecosystem, and
     - Are ready to absorb its operational complexity, or
     - Want to consolidate multiple existing Elastic/OpenSearch workloads with vector search.
3. <strong>Track engine evolution but avoid chasing every new index.</strong>

    

   - pg\_vectorsearch’s PRISM index and pgvectorscale’s DiskANN show promising memory and latency advantages[\[38\]](<https://encore.dev/articles/pgvector-vs-pinecone> "pgvector with HNSW index queries 1M vectors in 5-20ms at 95%+ recall")[\[51\]](<https://qdrant.tech/blog/qdrant-1.20.x/> "Qdrant 1.20 adds BM25 full-text search on indexed payload fields, combinable with dense vector search in hybrid queries")[\[1\]](<https://encore.dev/articles/pgvector-vs-pinecone> "pgvector vs. Dedicated Vector Databases: A Production Benchmark")[\[33\]](<https://supabase.com/blog/hybrid-search-postgres-pgvector> "pgvector supports hybrid search using Reciprocal Rank Fusion (RRF) to combine dense vector and BM25/FTS results")[\[37\]](<https://tigerdata.com/blog/pg_vectorsearch-scalable-open-source-vector-search-postgresql> "Per Tiger Data&#x27;s benchmarks, pgvector with pgvectorscale achieved 28x lower p95 latency and 16x higher throughput than storage-optimized Pinecone"), but they are still early‑stage or alpha in late 2026[\[3\]](<https://www.instaclustr.com/education/vector-database/pgvector-vs-qdrant-5-key-differences-and-how-to-choose/> "pgvector cannot push down filters into the vector index scan, so post-filtering may hurt performance")[\[4\]](<https://github.com/timescale/pgvectorscale> "pgvectorscale: It&#x27;s available in early alpha and isn&#x27;t yet production-ready")[\[112\]](<https://github.com/timescale/pgvectorscale> "pg_vectorsearch is alpha; meant for testing, not production").
   - Monitor their maturity and vendor support; do not anchor your near‑term architecture on them.

## 11 10. What Would Justify Moving Away From the Initial Choice?

Concretely, for your team, moving away from “Postgres as main search engine” is justified if <strong>two or more</strong> of the following become true:

1. <strong>Persistent latency SLO violations</strong> on org‑scoped searches (p95 end‑to‑end &gt;300 ms) for important tenants, after:

    

   - Tuning HNSW parameters (M, ef\_search);
   - Right‑sizing RAM;
   - Partitioning tables by tenant group;
   - Upgrading to pgvector ≥0.8 and confirming iterative scan behavior.
2. <strong>Operational pain from index maintenance</strong>, such as:

    

   - HNSW index rebuilds taking many hours and impacting availability;
   - Frequent VACUUM / REINDEX required due to bloat from updates;
   - Significant metrics pointing to buffer cache thrashing.
3. <strong>High‑selectivity filtered queries show clear recall issues</strong>, verified by manual evaluation, that you cannot fix by parameter tuning.
4. <strong>Substantial embedding churn</strong> (e.g., weekly re‑embeddings of large portions of the corpus) makes Postgres write performance and index rebuild windows unacceptable.

In that case, the next step is <strong>not</strong> to scrap Postgres, but to <strong>introduce Qdrant as the primary vector search engine alongside Postgres</strong>, and only consider more radical changes (e.g., OpenSearch as the central search layer) if your broader product strategy demands a consolidated search platform.
