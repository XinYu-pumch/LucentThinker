# Architecture Options

We compare three architectures: (A) **PostgreSQL + pgvector**, (B) **OpenSearch (self-managed or AWS)**, and (C) **Postgres for metadata + Qdrant for vector search**. PostgreSQL already stores business data; pgvector adds an HNSW or IVFFlat index on a `vector(1536)` column. OpenSearch (the Apache-licensed fork of Elasticsearch) now includes a k-NN plugin for vectors with HNSW or Faiss. Qdrant is a standalone Rust-based vector database that exposes a HTTP/gRPC API and can be run in cloud or self-hosted. All must support 5M text chunks (1536‐D) for ~2000 tenants, 50 QPS, sub-300ms p95. We examine **hybrid ranking**, **filtered search**, **permissions**, **index/memory**, **updates consistency**, **backup/recovery**, and **operations**, citing recent sources.

## Hybrid Ranking (Semantic + Keyword)

- **Postgres+pgvector**: You can store embeddings in a table and use full‐text (`tsvector`) for keywords. Hybrid search is manual: run a vector query and a text query separately, then fuse or re-rank results. For example, pgvector docs suggest using a CTE or ranking fusion (like Reciprocal Rank Fusion) to combine HNSW results with `ts_rank_cd()` on a `plainto_tsquery`. No built‐in hybrid scoring is provided by pgvector; it relies on SQL logic or an external re-ranker. Dimensionality 1536 is supported (pgvector natively handles up to 2000 dims).  
- **OpenSearch Vector Engine**: Supports *native hybrid queries*. You can index text fields (e.g. full-text with BM25) alongside a `knn_vector` field. OpenSearch APIs let you write a single query that scores by BM25 + vector similarity. AWS documentation explicitly notes combining Okapi BM25 and vector scores via hybrid scoring to improve relevance. In practice, OpenSearch normalizes and sums these scores internally. This simplifies hybrid ranking compared to stitching queries by hand.  
- **Qdrant**: Does not have a single-query hybrid score. Instead, it supports multi-stage fusion: for example, run a BM25 text query on a payload field, then re-score top candidates by vector distance (or vice versa). The docs recommend techniques like Reciprocal Rank Fusion or manual re-ranking to combine dense and sparse results. In short, Qdrant requires two queries or stages and post-processing to achieve hybrid ranking. (Some users report “Hybrid search (BM25)” as an upcoming feature, but as of late 2026 you would implement it externally.)

## Filtered Vector Search & Permissions

- **Multi-tenant filtering**: Every search must restrict results to certain org(s)/docs.  
  - *pgvector*: By default the vector index has no notion of other columns. A naive query like `SELECT * FROM docs WHERE org_id=? ORDER BY embedding <-> q LIMIT k` can return *fewer* than k rows because the HNSW scan may skip some org values. To ensure k results you must “iteratively scan” or use a CTE workaround: e.g. find nearest K ignoring org, then filter to K results. In practice, you’d include `WHERE org_id = X` in the query, but Postgres does **post-filtering** after the nearest-neighbor scan. This can miss some matching vectors unless scanning more than k. So pgvector filtering is possible but less precise; it may require tuning `hnsw.max_scan_tuples` or using iterative CTEs. (Partitioning by org_id is another approach, but 2000 partitions is heavy.)  
  - *OpenSearch*: Built-in support for filtered k-NN. The Lucene HNSW engine can apply a boolean filter *during* the kNN search (“efficient k-NN filtering”). OpenSearch docs describe an “efficient k-NN filtering” mode that ensures k results are returned even with filters. In practice, one adds a `filter` clause inside the `knn` query JSON so filtering is integrated. AWS/O’Search guidelines suggest using inline filters or `post_filter`, both supported (with slight performance trade-offs). OpenSearch is designed for faceted/filtered search, so combining org_id or other predicates with vector search works natively.  
  - *Qdrant*: Strong filtering support via **payload indexes**. Qdrant lets you index a “payload” field like `org_id`. A payload index is a structure that *extends* the HNSW graph, enabling filters to be checked during the search traversal. In other words, filtering by org can be done in one pass. The Qdrant docs explicitly note that payload-index filtering is efficient, unlike post-filtering: “A payload index extends the HNSW graph, allowing filtering criteria to be applied during the semantic search phase”. You just include a filter clause (e.g. `{"must": [...], "filter": [{"key": "org_id", "match": 42}]}`) and Qdrant prunes out other tenants as it searches. In summary, Qdrant and OpenSearch both **natively** support fast filtered search, whereas pgvector requires workarounds and risks missing results unless carefully tuned. Recent community benchmarks note that *“Qdrant handles filtered search particularly well… pgvector with proper indexing is solid.”*. 

## Indexing, Memory & Scale

- **Data size**: 5M vectors ×1536 dims at 4 bytes ≈ **30.7 GB** of raw floats, plus index overhead.  
- **pgvector**: The HNSW index is memory-hungry. By default Postgres will load the full HNSW graph into RAM, which can be several times the raw data size. Techniques exist to reduce footprint: use `halfvec` (16-bit floats) to halve storage and memory, or use binary quantization for a smaller index with re-ranking. Even so, a PG instance needs tens of GB RAM (shared_buffers etc). pgvector uses WAL, so it replicates naturally. Index build can be done `CONCURRENTLY` to avoid downtime, but building HNSW for 5M points will take time. On updates, Postgres can only rebuild (or incrementally add to) the HNSW; frequent large inserts may degrade performance unless you vacuum/reindex regularly. Scaling beyond a single machine requires sharding (e.g. Citus).  
- **OpenSearch**: The vector index (Lucene or Faiss) also consumes significant memory and disk. OpenSearch can use **memory-mapped Faiss** indexes on NVMe for cost efficiency. (AWS OpenSearch can be configured with compressed/quantized indexes.) In self-hosted, you choose instance sizes and may allocate e.g. 32–64 GB RAM per node. The index shards can also be sharded across nodes. Amazon’s docs note that Faiss (HNSW) can “memory map indexes and use OS cache, eliminating full memory loads”. In sum, OpenSearch can keep indexes partly on SSD.  
- **Qdrant**: By default keeps **vectors in RAM** and builds a full HNSW in memory for each shard. Qdrant docs caution that large collections can exhaust RAM: “By default Qdrant stores vectors in RAM for max performance, but as collections grow, keeping everything in memory becomes expensive.” They provide an on-disk mode: seldom-used vectors and parts of the graph can be offloaded to SSD. (Graph traversal will then incur I/O when needed.) For 5M vectors, one would likely deploy multiple shards with replication; a common recommendation is e.g. 12 shards (initially) so you can scale nodes as needed. Qdrant shards add overhead, but you can start with a few (each stores a segment of data). Use fast NVMe if offloading. Overall, Qdrant will need at least similar RAM (tens of GB) for HNSW, unless you actively use disk mode. 

## Updates & Consistency

- **PostgreSQL**: ACID writes via WAL. pgvector states it *uses WAL* so everything is durable and replicable. New documents (upserts) become immediately visible after commit. Search indices can lag only as long as the transaction; you can also control VACUUM and `REINDEX CONCURRENTLY`. There is no eventual-consistency window beyond a normal transaction’s commit. Maintaining low latency with 50 QPS updates (in addition to reads) will require tuning: e.g. smaller Wal segments, possibly multiple CPUs. Indexes should be created with CONCURRENTLY to avoid locking.  
- **OpenSearch**: Near-real-time. Writes (document creates/updates) go to an in-memory segment and are visible after the next refresh (default 1s). You can tune refresh interval or use manual refresh. So updates have up to ~1s latency by default. Search is always consistent within the last refresh. OpenSearch also replicates shards for HA. The k-NN index update model is similar: new vectors are added to the index (and then migrated to the HNSW structure on refresh). Frequent updates (50 QPS) are doable but can consume CPU for segment merges. AWS Serverless OpenSearch now offers both “NextGen” (fast, with ~10s refresh) and “Classic” modes; latency depends on that setting.  
- **Qdrant**: Exposes simple upsert and delete APIs. By default, writes are flushed to disk asynchronously. There’s no MVCC; Qdrant is “eventually consistent” at the point level (reads may briefly miss a just-written point until flush). Qdrant’s “strict mode” (disabled by default in OSS) can prevent queries on unindexed fields. In practice, if you upsert points, they become searchable almost immediately (it writes to a WAL-like segment then incorporates into in-memory index). For high update rates, you may need to tune segment size or use batching. Qdrant’s documentation and community note that heavy updates can temporarily degrade search, so planning shards and segment config is important. Overall, PG offers the strongest consistency guarantees, OpenSearch and Qdrant are more eventually-consistent (as typical for search engines), but usually within seconds or less.

## Backup and Recovery

- **PostgreSQL**: Mature tooling. Use periodic base backups (`pg_basebackup` or snapshot) plus continuous WAL shipping for point-in-time recovery. pgvector data is part of the database, so it’s backed up with PG’s usual methods. We can restore the entire DB easily.  
- **OpenSearch**: Supports snapshot & restore to S3/NFS. You can snapshot the index (including vectors and text) frequently. Restoring an OpenSearch cluster from snapshots is well-known (similar to Elasticsearch). (AWS OpenSearch Service provides automated snapshots as a feature.)  
- **Qdrant**: The Open Source Qdrant does not have a built-in “backup agent” as PG does, but it provides snapshot APIs. You can create a snapshot of each collection and download it to storage. (Table [44] shows OSS lacks automated backup, whereas Qdrant Cloud/Hybrid offers it.) In practice, one would script periodic snapshot creation and store those files off-server. Recovery means re-loading or restoring those snapshots via the API. It’s doable but requires custom work. Note: a Qdrant node with replication factor >1 can re-replicate data on restarts if desired, but to be safe you’d also use snapshots or cloud-managed backup.

## Operational Burden

For a 6-person engineering team, complexity matters.  

- **PostgreSQL+pgvector**: Likely easiest to *start* if you already use PG. No new service to operate beyond scaling the Postgres instance(s). You manage one cluster (maybe AWS RDS or similar) with vector indexes. Maintenance is familiar (Postgres tuning, backups, etc.). The downside: pgvector is relatively new, so you might need some performance tuning (shared buffers, work_mem, HNSW settings). Also monitoring ANN recall vs exact may need extra checks. Scaling to >1 node for HA or read replicas is standard. For tens-of-GB data, a robust instance (e.g. r6g.4xlarge or similar) might suffice initially. Using Postgres means you leverage its replication, backups, and ACID model. The team can leverage existing Postgres expertise, but they will have to learn pgvector nuances (like iterative scan, vacuum behavior).  
- **OpenSearch**: Operationally heavier. You need a cluster (at least 2–3 nodes for HA, each multi-GB memory) with the k-NN plugin. Setup, security (TLS, auth roles, possibly per-tenant), and maintenance (heap memory management, JVM tuning) are nontrivial. AWS OpenSearch Service can offload much of this, but then it’s a managed service (with associated cost model). OpenSearch offers built-in dashboards/monitoring, but compared to PG it’s a whole new stack. It *does* natively cover hybrid search and filters, which might reduce application logic. But the team will need skills in Elasticsearch-like monitoring, scaling shards, dealing with cluster state.  
- **Postgres + Qdrant**: Mixed. You keep PG for relational data (and maybe keyword indexes), and add Qdrant for vectors. This doubles the infrastructure. Qdrant clusters need their own scaling, backups, monitoring. On the plus side, Qdrant’s cloud can manage much of it if you pay for cloud service. In-house, you’d run one or more Qdrant nodes (likely a small cluster with RF=2). Qdrant’s operation is simpler than a full Elasticsearch cluster, but still requires managing shards and replicas. You’d have to implement data sync from PG to Qdrant (on each insert/update, push vector+payload to Qdrant). That is extra code or a CDC pipeline. For permissions, Qdrant relies on you passing the org filter each query. The team must learn Qdrant’s API and monitor its health, but Qdrant is designed to be developer-friendly. Overall, this is more complex than a single Postgres, but possibly simpler than full OpenSearch cluster. 

## Benchmarks and Evaluation

Published benchmarks vary. For example, one recent study reports for **1M vectors (1536D)**: pgvector (HNSW) ~12ms p95, Qdrant ~8ms p95, Weaviate ~22ms. It notes that pgvector with HNSW is *much faster* than older reports (it beat Qdrant in a Supabase test). Another source reports Qdrant often outperforms others when filters are applied. (However, different clusters and parameters give conflicting numbers — one 2026 summary even claims pgvector 48ms p95 at 1M while others show ~12ms.) The takeaway is: **benchmarks are highly sensitive to hardware, index settings (`ef_search`, `m`, sharding), and whether filters are used**. 

To make the right choice, we should benchmark on our actual data and queries. Key tests include: raw vector-only queries (unfiltered), filtered vector queries, text queries, and hybrid pipelines. Measure p50/p95 latency under load (e.g. 50 QPS concurrency), recall (do we get correct results), and throughput as data grows. Also measure index build/update time: e.g. time to insert or delete batches of docs. Monitor memory and CPU use as vectors scale. Since we need ~300ms p95, pay special attention to tail latencies.  

**Signs to re-evaluate** the choice include: sustained high latency or tail beyond 300ms even after tuning, recall drop (especially under filters), or operational pain (e.g. too much downtime for reindexing on updates). If Postgres proves easy and meets targets initially, it makes sense to start there given its simplicity (no new DB). But if we hit performance or multi-tenancy limits (e.g. pgvector can’t filter fast enough, or scaling beyond one instance becomes needed), migrating to a specialized engine is warranted. For example, if updates to pgvector block writes for long, or if query tail latency jumps under multi-tenant load, we’d consider Qdrant or OpenSearch. Early metrics on query times *with filters* and hybrid recall quality will be our guide.  

## Summary Recommendation

Given a team of six and existing PostgreSQL use, **starting with Postgres + pgvector** is reasonable for initial development. It avoids managing a new service and yields a unified data store. Configure an HNSW index, tune `work_mem`/`shared_buffers`, and test with realistic multi-tenant queries. Use half-precision or quantization if memory is tight. Enforce org filtering in queries and handle the iterative scan as needed. Meanwhile, set up metrics. If we find pgvector cannot meet the 300ms p95 (especially under filtered or hybrid queries), or if scaling becomes an issue, we can then introduce a vector DB. Qdrant is a lightweight next step (especially its cloud) with strong filtered-search support, whereas OpenSearch provides the richest feature set (native hybrid scoring, analytics) but at higher ops cost.  

In any case, monitor latency and recall closely. As benchmarks warn, pgvector’s performance can degrade on large indexes or many filters without tuning. If query throughput or update churn grows beyond comfortable levels, consider splitting search off from Postgres. A hybrid approach (Postgres for metadata + Qdrant for vectors) can then offer efficient filtered search, at the cost of some engineering overhead for syncing data and security. OpenSearch would be justified if we also need advanced full-text analytics and are willing to handle a cluster. The key is to **benchmark early** on our workload and use those metrics (latency vs recall under load) to trigger any migration.
